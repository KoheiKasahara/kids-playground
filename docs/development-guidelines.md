# 開発規約

> この文書は長期的な設計・運用方針を扱う。個別機能の最新仕様は GitHub Issue、現在の詳細挙動・パラメータは実装コードとテストを正とする。
> リポジトリ共通の作業手順は [AGENTS.md](../AGENTS.md)、ブランチ・PR・Auto-mergeの運用は利用環境で提示される Project Instructions を参照する。

`kids-playground` に新しい子ども向けミニゲームを追加・変更するときの共通規約です。ゲーム固有の楽しさを保つことを優先し、共通化は複数のゲームで意味と変更理由が一致する場合に限定します。将来用途だけを想定した抽象化や、巨大な汎用ゲームフレームワークは作りません。

## ディレクトリと責務

- 各ゲームの画面・固有ロジック・固有データ・テストは `src/games/<game-id>/` の中に閉じます。
- 複数ゲームで共通する部品（UIコンポーネント、クイズ共通ロジック、効果音などの横断機能）だけを共通レイヤーに置きます。
- 共通化する前に、少なくとも2つのゲームで同じ意味・同じ制約・同じ変更理由を持つことを確認します。
- 特定のゲームのためだけに共通基盤（共通コンポーネント・共通ロジック・ビルド設定など）を変更しません。そのゲーム側で吸収できないか先に検討します。

### 依存境界と既存例外

- ゲーム固有実装は自ゲーム内に閉じ、複数ゲームで使う処理は共通レイヤーを参照します。他ゲームの内部実装への新しい直接依存は追加しません。型だけのimport、再export、動的import、ゲーム内テストにも適用します。
- `src/games/shared/`・`quiz-core/`・`image-quiz/` は既存の共通レイヤーです。これらと `src/components/`・`audio/`・`physics/`・`speech/`・`utils/` の本番コードからゲーム固有実装へ依存しません。`gameCatalog.ts` からゲーム固有実装への依存も禁止します。
- ルートを組み立てる `src/app/` や全体検証用の `src/test/`、共通レイヤーの結合テストはゲームを参照できます。ゲーム固有テストから別ゲームへの依存は例外管理の対象です。
- `npm run check:boundaries` で `src` のJS/TSモジュール参照を検査します。相対パスとTypeScript設定で解決できるaliasを扱い、import先は文字列リテラルで記述します。CSS内部の参照、URL文字列、実行時の資源取得、推移的依存や循環依存の検査は対象外です。
- 一括改修を避けるため、導入時点の違反は [boundary-exceptions.json](../scripts/architecture/boundary-exceptions.json) に参照元・参照先・理由を固定します。新しいファイルへの適用やワイルドカードによる拡張はしません。依存を解消したら同じ変更で例外も削除します。既存依存先の変更時は参照元のゲームも検証します。
- 原則は例外追加ではなくゲーム内への配置か、上記の共通化基準に従った共通レイヤーへの抽出です。やむを得ない例外変更は、理由・影響範囲・検証結果をレビューで説明します。検査は `lint` に含まれ、通常CIでも実行されます。

## ゲームを追加するときの手順

1. ゲームカタログにエントリを追加する（表示用の説明とSEO用の情報を両方含める）。
2. ルート定義を追加する。新しいゲームは軽量なものも原則 `React.lazy` / 動的importで登録し、未選択ゲームのコード・CSSをホームへ積み上げない。ゲームカタログはデータのみを保ち、そこからゲーム実装をimportしない。
3. ホーム画面から遷移できることを確認する。
4. そのゲームのルートが存在すること・主要な遊びのループが1本通ることをテストで確認する。

新しいゲームごとに個別のdocsを必ず作成する必要はありません。`docs/games/` に資料があるかどうかはゲームの重要度を意味せず、コードとテストだけで十分に理解できるゲームには資料を作らない方針です。

## 幼児向けUIとアクセシビリティ

- ひらがな中心の平易な文言にし、文字量を抑える。
- 文字を読めなくてもある程度操作できるようにする。
- スマートフォンの縦画面での利用を優先する。
- 主操作のタップ領域を十分大きく取り、誤操作しにくい余白を確保する。
- 正誤や状態は色だけに頼らず、記号・文言・アニメーションなど複数の手がかりを併用する。
- キーボード操作やフォーカス表示など、タッチ以外の操作手段も損なわない。
- 具体的な数値（px・秒数など）はここに書かず、実装済みの共通コンポーネントを正とします。

## 音声・読み上げの扱い

- 音声読み上げは補助として扱い、必須にしない。
- 音が出ない・無効化されている環境でもゲームが成立することを確認する。
- 音量設定など、ユーザーが制御できる手段を用意する。

## 効果音と音量のそろえ方

- 音のないゲームは作らない。主な操作（タップ・おく・せいかい・クリアなど）には効果音をつけ、音は最初から ON にする。
- 効果音は `audio/sound` の共有 AudioContext で鳴らし、`ctx.destination` ではなく `getSoundOutput(ctx)` へつなぐ。共通の出口で、ゲームごとの音量補正と音割れ防止のリミッターがかかる（直接 `destination` へつなぐとテストで失敗する）。
- ゲーム内の「おと」ボタンで全体の ON/OFF を切り替えるときは `useSoundToggle` を使い、画面を離れたら ON に戻す。ほかのゲームまで無音にしない。
- ゲームを追加したら、よく鳴る代表音を `src/test/audio/gameSoundSamples.ts` に登録する。`src/audio/gameSoundLevels.test.ts` が実際に描き起こして騒音計と同じ方法で大きさを測り、次を確かめる。
  - そのゲームでいちばん大きい代表音が、ほかのゲームと同じくらいの大きさであること（ずれていたら、失敗メッセージに出る補正値を `src/audio/gameSoundLevels.ts` に書く）。
  - 代表音が小さすぎて聞こえないものがないこと（そのときは効果音の音量を上げる）。
  - BGM・走行音などの鳴り続ける音が、効果音より小さいこと。
- 目標の大きさ・許容幅などの数値はここに書かず、`gameSoundLevels.ts` とテストを正とする。

## 2D / 3D物理を使うゲームでの共通注意

- 物理エンジンの内部状態を画面コンポーネントへ直接持ち込まず、フックなどの層を挟んで結果だけを受け取る構造にする。
- 物理パラメータや座標系はそのゲームの実装に閉じ、docsへ転記しない。
- 物理エンジンを動かさずに単体テストできる部分（データ定義や純粋関数）は分離してテストする。

## 素材・権利・プライバシー

- 新しい画像・音源を追加したら [credits.md](./credits.md) を必ず更新する。
- 外部素材を利用する場合は、再配布・加工が許されるライセンスの素材だけを採用し、出典・ライセンスを確認する。
- 人物の顔や個人が特定できる情報、判読可能な車両番号など、子ども向け用途にそぐわない素材は避ける。

## PWA・オフラインとの整合

- 新しい大きな静的素材を追加するときは、オフラインでの利用継続とキャッシュ容量への影響を確認する。
- 新しいファイル種別の素材を追加する場合は、キャッシュ対象の設定を確認する。

## 品質ゲート

ゲームの実装・挙動を変更するときは、変更に関係する次の品質を確認します。実行するコマンドと文書のみの変更を含む適用範囲は [変更別の検証](./setup.md#変更別の検証) を正とします。

- データの整合性（重複がないこと、参照する素材が実在すること）をテストで確認する。
- 画面遷移・回答・進行・結果表示・再挑戦など、そのゲームの主要な遊びのループをテストで確認する。
- 不正なURLパラメータや、必要な状態を持たずに深いURLへ直接アクセスした場合の挙動を確認する。
- `lint` / 型チェック / テスト / `build` が通ることを確認する。

個別のテストケースの一覧はここには書かず、テストコード自体を正とします。

## ドキュメントの扱い

docsには次のような、変更頻度が高く陳腐化しやすい情報を書きません。

- 問題数・ステージ数・国の数などの具体的な数値
- 物理パラメータ・座標・UI寸法などの実装の詳細値
- 作業のフェーズ番号・実装順序・引き継ぎ事項・今後の予定・TODO
- 個別のテストケースや受け入れ条件の列挙

これらは GitHub Issue、または実装コードとテストを正とします。

### ゲーム追加・変更時の共通基盤

- 登録は `gameCatalog.ts` のデータと中央 `routes.tsx` の入口。複数画面がある新ゲームは `color-mix-quiz/routes.tsx` の相対ルート＋画面ごとのlazy importを参考にする。既存URLは維持し、全ゲームをまとめて移行しない。
- ディレクトリは `src/games/<slug>/` に入口、必要に応じて `routes.tsx`、画面、ゲーム固有 `sounds.ts` / physics / data を置き、テストを対象ファイルの隣に置く。短いゲームを形式のために分割しない。
- 戻る導線は各画面が自分のヘッダーへ `GameBackButton` を置き、`to` または `onBack` で一階層上を明示する。safe-area付きの既存ヘッダーの左端へ配置する（ボタン側ではsafe-areaを重ねない）。Appが重ねる共通の戻るボタンは `src/app/appGameBackButton.ts` に挙げた未移行の既存画面にだけ残し、新しいゲームはそこへ追加しない。ヘッダーへ移した画面は同じ変更で一覧から外す。
- `useGameIntroPlaying` は単一路線の選択→プレイ切替に利用できる。ボウリングではプレイ中のみ共通説明を隠し、「もどる」で選択画面と説明を復元する。初期表示と静的HTMLの本文は維持する。
- Rapierはlazy側から `physics/rapierLoader` で初期化。初期化失敗は呼出元に伝え、次の呼出しで再試行する。world・step・free、RAF、イベント、GPU資源はゲームが所有し、effect cleanupで対応する資源を解放する。非同期完了は退出済みなら新しいworldを開始しない。
- 新しいSEはゲーム内へ。`audio/sound` の共有Context・mute・primeAudio・短音・共通の出口（`getSoundOutput`）を利用し、ゲーム退出時に共有Contextをcloseしない。既存 `quizSound` の未移行SEは次に触るときに移す。音量のそろえ方は「効果音と音量のそろえ方」を参照する。
- Quickには純粋ロジックの境界と代表DOM遷移（開始・操作・リセット・退出）、資源を持つゲームにはcleanup/再入場の回帰検査。広いseed・完走・分布はFull。ピンボールでは既存網羅試行を `pinballSimulation.full.test.ts` に残す。
- E2Eはカタログ由来の全入口smokeと、Nightlyの代表3D・横向き実操作。ゲーム追加ごとに全操作E2Eを複製しない。変更時の実行範囲は [変更別の検証](./setup.md#変更別の検証) を参照する。
- CI Summaryの遅いファイル上位は既存Vitest JSONの開始・終了時刻を使う。並列実行のファイル時間を足してCI時間と扱わない。
- 振動は `utils/haptics` の `vibrate('tap' | 'impact' | 'success' | 'error' | 'celebrate')` を使う。非対応端末・動きを減らす設定・ホームの「ぶるぶる」OFFでは何もしないので、ゲーム側で分岐しない。
- ステージ制の「クリア済み＋★」は `games/shared/progress/stageProgress` の `createStageProgressStore` で保存し、選択カードには `StageClearBadge` を添える。★の基準はゲームごとに決める。
- クイズの正誤演出（中央の○×・紙吹雪・振動・不正解時の答えの読み上げ）は `QuizResultOverlay` が持ち、結果画面の★は `QuizStars` を使う。
- プレイ中の画面（`/games/...`）では、PWAの完了・更新トーストを出さずホームへ戻るまで遅らせる。
