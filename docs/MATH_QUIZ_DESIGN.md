# 「さんすうクイズ」基本設計

## 1. 目的と対象

たしざん・ひきざん・かけざん・わりざんの計算式を表示し、正しい答えを選ぶ4択クイズです。
子ども向けのため、既存の「こっきクイズ」「はたらくくるまクイズ」と同じく写真や図案を使う方式も検討できますが、
さんすうクイズでは計算そのものを覚える・慣れることが目的のため、問題は写真ではなく計算式（例: `3 ＋ 4 = ?`）で出題します。

学習のねらいは、四則演算に親しむことです。九九や繰り上がり・繰り下がりのある計算を、ゲーム感覚で繰り返し解けるようにします。

バックエンドや外部APIは使わず、出題データはすべてアプリ内で計算して生成します（画像・音声などの静的素材の同梱もありません）。

既存2ゲーム（こっきクイズ、はたらくくるまクイズ）が「写真・図案 ⇔ 名前」を4択で当てるゲームであるのに対し、
さんすうクイズは「計算式 → 答えの数値」を4択で当てるゲームという位置づけです。
選択肢が既存データの別要素ではなく計算によって作られる数値である点が、既存2ゲームとの大きな違いです（詳細は7章）。

## 2. モードとむずかしさ

4モード × 3むずかしさの組み合わせで出題します。モードは演算そのものです（`MathQuizMode = MathOperation`）。

| 内部名 (`MathOperation`) | 表示 (`MODE_LABEL`) |
| --- | --- |
| `add` | たしざん |
| `sub` | ひきざん |
| `mul` | かけざん |
| `div` | わりざん |

むずかしさ選択画面には、`LEVEL_DESCRIPTION`（モード×むずかしさの出題内容の説明文）を表示します。実際の文言は次のとおりです。

| モード \ むずかしさ | かんたん (easy) | ふつう (normal) | むずかしい (hard) |
| --- | --- | --- | --- |
| たしざん | 1けたの けいさん | 20までの けいさん | 2けたの けいさん |
| ひきざん | 1けたの けいさん | 20までの けいさん | 2けたの けいさん |
| かけざん | 1から5の かけざん | くく ぜんぶ | 2けた × 1けた |
| わりざん | 1から5で わる | くくの ぎゃく | 2けた ÷ 1けた |

1ゲームは`QUESTION_COUNT`（quiz-core由来、10問）、選択肢数は`CHOICE_COUNT`（quiz-core由来、4択）です。
1ゲーム内で正解の計算（`problem.id`）は重複せず、各問題の選択肢は重複なしの4件で正解を1件だけ含みます。

## 3. URLと画面遷移

| 画面 | URL |
| --- | --- |
| 開始・モード選択 | `/games/math-quiz` |
| むずかしさ選択 | `/games/math-quiz/<mode>` |
| プレイ | `/games/math-quiz/<mode>/:level/play` |
| 結果 | `/games/math-quiz/<mode>/:level/result` |

`<mode>` は `add` / `sub` / `mul` / `div`（`MODE_PATH` の値、モードの内部名と同じ）です。`:level` は `easy` / `normal` / `hard` です。

`src/app/routes.tsx` には、開始画面1件 + 4モード ×（むずかしさ選択・プレイ・結果の3件）で、合計13件のルートが登録されています（配列 `MATH_QUIZ_MODES` から `flatMap` で組み立てているため、直書きの繰り返しはありません）。

不正な `:level`（URL直打ちなど）は `MathQuizPlay` 内の `isQuizLevel` チェックにより、そのモードのむずかしさ選択画面へ `replace` で戻します。
結果画面（`/result`）は正解数などの遷移 state に依存しており、state なしで直接アクセスした場合は `MathQuizResult` 内の `isResultState` チェックにより開始画面（`/games/math-quiz`）へ戻します。結果画面URLの `:level` が不正な場合は、そのモードのむずかしさ選択画面へ戻します。

画面遷移は次のとおりです。

```text
ホーム → 開始（モード選択） → むずかしさ選択 → 10問プレイ → 結果
                                    ↑                     │
                                    └──── べつのむずかしさ ──┘
```

結果画面からは「もういちど（同じモード・むずかしさで再プレイ）」「べつのむずかしさ（むずかしさ選択へ）」「べつのけいさん（モード選択=開始へ）」「ホームへ」の4つに遷移できます（`MathQuizResult.tsx`）。

## 4. 画面仕様

### 4.1 開始（`MathQuizStart.tsx`）

- タイトル「さんすうクイズ」、「ぜんぶで 10もん あるよ」の説明を表示する。
- 4モードのボタンをそれぞれ絵文字（`MODE_EMOJI`）とラベル（`MODE_LABEL`）で表示する。
- 「もどる」でホームへ戻る。

### 4.2 むずかしさ選択（`MathQuizLevelSelect.tsx`）

- 見出し「むずかしさを えらんでね」と、選択中のモードのラベルを表示する。
- かんたん／ふつう／むずかしいの3段階を、星（`LEVEL_STARS`）・むずかしさラベル（`LEVEL_LABEL`）・`LEVEL_DESCRIPTION`の説明文で示す。
- 選択後は該当モード・むずかしさのプレイURLへ移動する。「もどる」でモード選択（開始画面）へ戻る。

### 4.3 プレイ（`MathQuizPlay.tsx`）

- ヘッダーに「やめる」ボタン（固定表示）、現在のむずかしさラベル、`現在 / 10`、進捗バーを表示する。
- 本体に計算式を見出し（`<h1>`）として `{left} {演算記号} {right} = ?` の形式で表示し、その下に選択肢4件を2列グリッドで表示する。
- 回答後は全選択肢を無効化し、正解のボタンには緑系の枠と `◯`、選んだ誤答のボタンには赤系の枠と `✕` を付ける。
- 画面下部の固定領域（共通コンポーネント`QuizResultOverlay`）に正誤メッセージ（「🎉 せいかい！」/「ざんねん！」）と正解の数値（「こたえ: {answer}」）、次の操作ボタンを表示する。下部余白は回答したかどうかに依存させず、ビューポートの幅・高さだけで決める（`PanelFlagQuizPlay`と同じ4系統。詳細は`docs/PANEL_FLAG_QUIZ_DESIGN.md`参照）。
- 最終問（10問目）の次操作ボタンは「けっかを みる」に変わる。

### 4.4 結果（`MathQuizResult.tsx`）

- 見出し「けっか」、モードとむずかしさ、正解数（「{correctCount} / {totalCount}もん せいかい！」）を表示する。
- 正解数に応じた成績メッセージ（`getPraise`）を表示する。10/10は🏆「かんぺき！」、7以上は🎉「すごい！」、4以上は👍「よくできました」、それ未満は😊「またあそぼう！」の4段階。
- 「もういちど」「べつの むずかしさ」「べつの けいさん」「ホームへ」の4経路を用意する。

## 5. 出題プール

出題プールは演算・むずかしさごとに、条件を満たす計算をすべて列挙してから抽選する方式です（`src/games/math-quiz/data/problemPool.ts`）。
各プールの条件式と実件数（`problemPool.test.ts` の `EXPECTED_COUNT` が正）は次のとおりです。

| 演算 | むずかしさ | 条件式 | 件数 |
| --- | --- | --- | --- |
| たしざん (add) | easy | `1 <= left, right <= 9` | 81 |
| たしざん (add) | normal | `1 <= left, right <= 20` かつ少なくとも片方が2けた | 319 |
| たしざん (add) | hard | `10 <= left, right <= 99`（2けたどうし） | 8100 |
| ひきざん (sub) | easy | `1 <= right < left <= 9` | 36 |
| ひきざん (sub) | normal | `1 <= right < left <= 20`（左辺は2けた） | 154 |
| ひきざん (sub) | hard | `10 <= right < left <= 99` | 4005 |
| かけざん (mul) | easy | `1 <= left, right <= 5` | 25 |
| かけざん (mul) | normal | `1 <= left, right <= 9`（九九ぜんぶ） | 81 |
| かけざん (mul) | hard | `1 <= left <= 99` かつ `1 <= right <= 9` | 891 |
| わりざん (div) | easy | わる数 `1 <= right <= 5`、商 `1 <= quotient <= 5`、`left = right × quotient` | 25 |
| わりざん (div) | normal | わる数 `1 <= right <= 9`、商 `1 <= quotient <= 9` | 81 |
| わりざん (div) | hard | わる数 `1 <= right <= 9`、`right × quotient <= 99` | 277 |

### なぜ全列挙 → 抽選なのか

出題のたびにランダムに数値を生成して重複を弾く方式だと、重複判定のためのリトライや既出管理が必要になり実装が複雑になります。
条件を満たす計算をあらかじめ全列挙してから `pickRandom`（quiz-core、Fisher–Yatesシャッフル+`slice`）で抽選する方式にすると、
「1ゲーム内で正解の計算が重複しない」ことが「配列から重複なしで取り出す」という構造そのものによって保証されます。
また、この方式なら「件数がちょうど何件か」「あるむずかしさの全問題が上位のむずかしさに含まれるか（包含関係）」をテストで直接検証できます（`problemPool.test.ts`）。

### 難易度ごとの出題範囲

たしざん・ひきざんは、数字の桁数で難易度を分けます。かんたんは0を使わない1けたどうし、ふつうは20までで少なくとも片方が2けた、むずかしいは2けたどうしです。引き算は常に左辺を右辺より大きくして、答えを1以上にします。

かけざん・わりざんは従来どおり easy ⊂ normal ⊂ hard の範囲を保ちます。`problemPool.test.ts` では、足し算・引き算の桁数・0不使用・正の答えと、かけ算・割り算の包含関係をそれぞれ検証しています。

### 答えは1以上の整数、わりざんはあまりなし

全レベル・全演算で `answer` は1以上の整数になるように問題の条件が作られています。足し算・引き算では0をオペランドに使わず、ひきざんは `right < left` を条件にして答えが0以下にならないようにします。
わりざんは商から `left = right × quotient` を逆算して問題を作るため、あまりが出ません。
これは子ども向けのため、対象年齢がまだ習っていない・理解しづらい0を足す・引く計算、答えが0以下になる計算、あまりのある除算を出題に含めないという設計判断です。
`problemPool.test.ts` が、全問題の `answer` が1以上の整数であること、足し算・引き算で0をオペランドに使わないこと、ひきざん全件で `left > right` であること、わりざん全件で `right >= 1` かつ `left % right === 0` であることを検証しています。

### プールが遅延生成＋キャッシュである理由

4演算 × 3むずかしさ = 12プールの件数を合計すると14,075件（add: 81+319+8100=8500、sub: 36+154+4005=4195、mul: 25+81+891=997、div: 25+81+277=383）になります。
これをモジュール読み込み時にまとめて生成すると、さんすうクイズを一度も遊ばない利用者にとってもアプリ起動が重くなってしまいます。
そのため `problemsFor(operation, level)` は演算・むずかしさの組み合わせごとに `Map` でキャッシュし、実際にアクセスされた組み合わせだけを初回にその場で生成します
（実装コメントでは概数として「約14,000件」と説明されています）。

## 6. 誤答（ダミー選択肢）の作り方

誤答は `buildDistractors`（`src/games/math-quiz/questionGenerator.ts`）が作ります。当てずっぽうが効きすぎる純粋な乱数値ではなく、
「子どもが実際にやりがちなまちがい」を候補にすることで、学習効果のある誤答選択肢にする狙いがあります（実装コメントに明記）。

候補（`raw`）は共通候補に演算ごとの追加候補を足して作ります。

- 共通候補（全演算）: `answer + 1`, `answer - 1`, `answer + 2`, `answer - 2`, `answer + 10`, `answer - 10`
- たしざん (add): `answer - 10`, `left + right + 10`（コード上は共通候補や `answer + 10` と実質重複するため、重複除去に委ねている、と実装コメントに明記されている「繰り上がり忘れ」を意図した候補）
- ひきざん (sub): `right - left`（左右を取り違える符号のまちがい）, `left + right`（引き算のつもりで足してしまうまちがい）
- かけざん (mul): `answer + left`, `answer - left`, `answer + right`, `answer - right`（九九表で1マスずれた値を選んでしまう「九九の隣」のまちがい）, `left + right`（掛け算のつもりで足してしまうまちがい）
- わりざん (div): `left - right`（割り算のつもりで引いてしまうまちがい）, `right`（商ではなくわる数自体を答えてしまうまちがい）

フィルタ条件: 整数であること、0以上であること、正解 (`answer`) と一致しないこと、既に採用済みでないこと（`Set`で重複排除）を満たす値だけを候補として残します。
残った候補を `shuffle` でシャッフルしてから、必要な件数（`CHOICE_COUNT - 1` = 3件）だけ `slice` します。

補充ロジック: 正解が `1` のときなど、フィルタ後の候補が必要数に満たない場合があります。その場合は `answer + 1` から順に、まだ使われていない非負整数を探して足りない分を埋めます
（`filler` 変数をインクリメントしながら `used` 集合にない値を追加）。これにより `answer === 1` のケースでも必ず指定件数の誤答が返ります（`questionGenerator.test.ts` のエッジケーステストで保証）。

## 7. quiz-core との関係

### なぜ `QuizQuestion<T>` を使わず `MathQuestion` を独自定義したのか

既存の国旗クイズ・はたらくくるまクイズは、正解も誤答も同じマスタデータ（国データ、車両データ）の別要素であり、
`QuizQuestion<T extends Identifiable>`（`{ answer: T; choices: T[] }`）というID付きデータの集合として自然に表現できます。

一方、さんすうクイズの誤答は「実在する別の問題」ではなく、正解の数値に対して「近傍の数値」（+1、九九の隣など）を計算して作る値であり、
それ自体は出題される予定のない計算（`MathProblem`）ではありません。これを無理に `QuizQuestion<MathProblem>` に載せようとすると、
誤答のためだけに実際には出題されない架空の `MathProblem`（`id`・`left`・`right`を持つが実在しない計算）をでっち上げることになり、データの意味が壊れます。

そのため `src/games/math-quiz/types.ts` に、正解の計算1件と数値の選択肢配列だけを持つ専用の型 `MathQuestion = { problem: MathProblem; choices: number[] }` を定義しました。

これは `MINIGAME_DEVELOPMENT_GUIDELINES.md` §2「共通化は複数ゲームで意味と変更理由が一致する最小単位に限定する」に沿った判断です。
「選択肢の意味」（既存データの別要素 vs 計算で作られる近傍の数値）が既存2ゲームとさんすうクイズで一致しないため、`QuizQuestion<T>` を無理に流用せず専用型を切りました。

### 再利用しているもの

- `quiz-core/questionGenerator.ts` の `shuffle`・`pickRandom`: Fisher–Yatesシャッフルと重複なし抽選そのものは、演算にもデータ形にも依存しない汎用処理なのでそのまま使います。
- `quiz-core/types.ts` の `QuizLevel`・`isQuizLevel`・`LEVEL_LABEL`・`LEVEL_RANK`・`LEVEL_STARS`・`QUESTION_COUNT`・`CHOICE_COUNT`: むずかしさの3段階、URLの型ガード、表示ラベル、星、1ゲーム10問、1問4択という意味は既存2ゲームと完全に一致するため、`src/games/math-quiz/types.ts` でそのまま再エクスポートして使っています。

`quiz-core`（`types.ts`・`questionGenerator.ts`）自体は、さんすうクイズの追加にあたって一切変更していません。

## 8. UI・アクセシビリティ

- 式の表示: `OPERATION_SIGN`（`add: ＋`, `sub: −`, `mul: ×`, `div: ÷`）の全角記号を使い、`{left} {演算記号} {right} = ?` の形で見出し（`<h1>`）として表示する。
- 数字の見やすさ: 式（`.question`）と選択肢（`.choiceButton`）には `font-variant-numeric: tabular-nums`（等幅数字）を指定し、式はさらに `ui-monospace` 系のフォントスタックで桁がそろうようにしている。サイズはビューポート追従の `clamp()` で決め、式は `clamp(40px, 13vw, 68px)`、選択肢の数字は `clamp(26px, 8vw, 36px)`。
- 選択肢レイアウト: `.choices` は `display: grid; grid-template-columns: repeat(2, minmax(0, 1fr))` の2列グリッドで、`.choiceButton` は `min-height: 72px` のタップ領域を確保している。
- 色以外のフィードバック: 回答後は `choiceVariant` で正解ボタンを `correct`、選んだ誤答ボタンを `wrong`、その他を `secondary` にし、`choiceMark` で正解には `◯`、選んだ誤答には `✕` をボタン文字列の先頭に付ける（色だけに頼らない）。
- 回答結果の通知: 画面下部固定の `QuizResultOverlay` に `role="status"` と `aria-live="polite"` を付け、正誤メッセージと「こたえ: {answer}」をスクリーンリーダーへ通知する。
- 装飾絵文字: 開始画面のヒーロー絵文字とモードボタンの絵文字（`MODE_EMOJI`）、むずかしさ選択の星（`LEVEL_STARS`）、結果画面の成績絵文字はすべて `aria-hidden="true"`。
- 狭い縦画面: `@media (orientation: portrait) and (max-height: 620px)` でプレイ画面の式・選択肢のフォントサイズと高さを縮小する（オーバーレイ`QuizResultOverlay`自体の縮小は共通CSS側で行う）。開始画面は `@media (max-height: 700px)` でヒーロー絵文字と余白を詰める。
- 低い横画面: `@media (orientation: landscape) and (max-height: 560px)` で、プレイ画面は本体を横並び（`flex-direction: row`）にする（`QuizResultOverlay`もテキスト＋ボタンの横並びになる）。開始画面はヒーロー絵文字を非表示にしてボタンを2列グリッドに、むずかしさ選択画面は3列グリッドにする。
- 選択肢・ナビゲーションはネイティブ `button`（`BigButton` コンポーネント）を使い、タッチとキーボードの両方に対応する。

## 9. 効果音

`src/utils/quizSound.ts` の `playCorrectSound` / `playIncorrectSound` をそのまま流用します。この関数はWeb Audio APIで正解音・不正解音をその場で合成しており、音声ファイルを追加せずに動作します。
国旗クイズ・はたらくくるまクイズと共通の実装で、さんすうクイズのための変更は行っていません。`MathQuizPlay.tsx` は正解選択時に `playCorrectSound()`、不正解選択時に `playIncorrectSound()` を呼びます。

## 10. 素材

さんすうクイズは新規の静的素材（画像・音声ファイルなど）を追加しません。式と選択肢はすべて数値としてその場で計算・表示し、効果音もWeb Audio APIによる合成音（9章）を流用するためです。
したがって、`public/` への素材追加、`vite.config.ts` のWorkbox `globPatterns` の変更、`docs/CREDITS.md` の更新はいずれも不要です。

## 11. テスト

`problemPool.test.ts` / `questionGenerator.test.ts` / `MathQuiz.test.tsx` が保証している内容を、`MINIGAME_DEVELOPMENT_GUIDELINES.md` §8 の品質ゲート項目と対応付けると次のとおりです。

### `problemPool.test.ts`（§8-1 データ件数の確認、§8-2 むずかしさ別件数と累積包含関係の確認）

- 4演算 × 3むずかしさ = 12通りそれぞれで、件数が `EXPECTED_COUNT` どおりであること、`id` が重複しないこと
- 各プールが10件以上あること（§5「出題プールは…10問ゲームでは原則10件以上を品質ゲートとする」）
- `answer` が1以上の整数で、演算結果と一致すること
- 足し算・引き算のかんたん・ふつう・むずかしいが、それぞれ定義された桁数の範囲で、0をオペランドに使わないこと
- ひきざん全件で `left > right` であること（答えを1以上にする制約）
- わりざん全件で `right >= 1` かつ `left % right === 0` であること（あまりなし制約）
- かけ算・割り算で easy ⊂ normal ⊂ hard が成り立ち、件数が真に増えること
