# こっきコロコロパズル 基本設計（Phase 1）

Issue #165「【新ミニゲーム案】こっきコロコロパズル（2D・パーツ配置でゴールを目指す）」の
**Phase 1：ゲーム基盤・最小プレイアブル版** に対応する設計です。

Phase 2以降（途中停止からの編集再開、配置済みパーツの移動・回転・削除、パーツ拡充、演出）は
まだ実装していません。この文書は、その拡張が入る前提で「どこに何を足せばよいか」を残すことを目的にしています。

## 1. ゲームの目的と対象

- 対象: 幼児（説明を読まずに触って遊べること）
- 遊びかた: 盤面へ板を置いて道を作り、上から落とした国旗ボールを下のゴールへ導く
- 正解ルートは1つではない。外れても失敗表示は出さず、ボールを戻して置き直すだけ

## 2. 画面とURL

```text
/games/flag-roll-puzzle    プレイ画面（1画面のみ）
```

- ホームのカード「こっきコロコロパズル」から遷移する。
- 画面は1つだけで、開始画面・結果画面は持たない（こっきドミノと同じ構成）。
- 物理エンジン(matter-js)を含むため、`src/app/routes.tsx` で `lazyRoute` により遅延読込する。

画面構成（スマホ縦画面が基本）:

```text
ヘッダ（やめる / タイトル）
2Dゲームボード（上：スタート帯 / 中央：配置グリッド / 下：ゴール帯）
ひとこと（role="status"）
パーツ置き場
「ボールを おとす！」/「ボールを もどす」・「ぜんぶ けす」
```

低い横画面では、盤面を左・操作まわりを右へ並べ替えて盤面の高さを確保する（CSSの
`@media (max-height: 560px) and (orientation: landscape)`）。

## 3. 盤面の座標系

盤面は論理座標（`boardLayout.ts`）だけで組み立て、実機の画面サイズへは
`useBoardScale` が返す倍率ぶんの CSS `transform: scale()` で合わせます。
物理パラメータをこの1つの座標系で調整すれば、どの端末でも同じ挙動になります。

| 値 | 意味 |
| --- | --- |
| `CELL_SIZE = 60` | 配置グリッド1マスの1辺 |
| `GRID_COLS = 6` / `GRID_ROWS = 8` | 配置グリッドの列数・行数 |
| `GRID_TOP = 72` | スタート帯の高さ（＝グリッド上端） |
| `GOAL_HEIGHT = 68` | ゴール帯の高さ |
| `BALL_RADIUS = 20` | 国旗ボールの半径 |
| `GOAL_AREA` | 盤面下端の左寄り2マスぶん |

- 盤面の幅・高さは上の基本値から導出するので、マスの大きさや行数を変えれば盤面全体が追従します。
- 行数を増やすほどコースは長くなりますが、スマホ縦画面では1マスが小さくなります（盤面全体が
  画面の高さに合わせて縮むため）。8行は iPhone 相当の縦画面で1マスが50px前後を保てる上限です。
- 国旗ボールの開始位置 `BALL_START` は「中央に最も近い列の中心」です。列数が偶数のとき盤面の
  ちょうど中央は列の境目にあたり、真下の板の端ばかりに当たって結果が読みにくくなるためです。
- ゴールを盤面いっぱいにしないのは、まっすぐ落とすだけで到達してしまい「ななめ板で向きを変える」
  遊びが成立しなくなるためです。外したボールは床に残るだけで、失敗の表示はしません。

## 4. パーツの表しかた（拡張の中心）

`partTypes.ts` の `PartDefinition` が、1種類のパーツに関する情報をすべて持ちます。

```ts
type PartDefinition = {
  id: PartTypeId          // 種類
  label: string           // パーツ置き場に出す名前
  cells: GridCell[]       // アンカーセルからの相対で、占有するマス
  segments: PartSegment[] // 形（長方形の並び。中心からの相対位置・大きさ・角度）
  restitution: number     // 物理係数
  friction: number
}
```

Phase 1のパーツは3種類です。名前は「見た目の向き」ではなく **ボールがどちらへ滑るか** で付けています。

| id | ラベル | 形 | 占有マス |
| --- | --- | --- | --- |
| `plank` | よこいた | 横板 | 1 |
| `slopeLeft` | ひだりへ | ／（右端が上がる） | 1 |
| `slopeRight` | みぎへ | ＼（右端が下がる） | 1 |

設計上の要点:

- **描画と物理Bodyを同じ `segments` から作る**。`PartShape`（描画）も `usePuzzleEngine` の
  `partBodies`（物理）も同じ定義を読むので、見た目と当たり判定が構造的にずれません。
- **パーツ種類ごとの分岐をゲーム本体に置かない**。パーツ置き場は `PART_DEFINITIONS` を並べるだけ、
  物理世界は `segments` を長方形にするだけです。新しいパーツは定義を1件足せば動きます。
- **占有マスは配列で持つ**。Phase 3で予定している2〜3マスを使う長い板は、`cells` に
  オフセットを足すだけで重なり判定・ボード外判定に反映されます。
- カーブのように長方形で表しにくいパーツが必要になったら、そのときに
  セグメントを細かく分けるか、描画専用の情報を足します。今は使わない仕組みを先には作りません。

## 5. 配置ロジック

`grid.ts` と `placement.ts` に、UIから独立した純粋関数として置いてあります。

- `nearestCell(point)`: 論理座標を最寄りのマスへスナップする。等間隔グリッドでは
  「その点を含むマス」が「中心が最も近いマス」と一致するため、切り捨てで求まります。
  グリッドの外を指した場合は端へ寄せず、範囲外のマスをそのまま返します（押した場所と
  違うところにパーツが出ないようにするため）。
- `isInsideBoard(typeId, anchor)`: 占有マスがすべてグリッド内か（ボード外への配置を拒否）。
- `overlapsExistingPart(parts, typeId, anchor)`: 既存パーツとの重なり。
- `canPlacePart` / `placePart`: 上の2つをまとめた判定と、置けたときだけ新しい配列を返す関数。
  置けない場合は例外ではなく `null` を返し、呼び出し側が「元の場所へ戻す」挙動を選べるようにします。
- `boardPointFromClient`: 画面上のポインタ座標を、盤面の拡縮を打ち消して論理座標へ戻す。

操作は2通りあります（どちらも同じ `place()` に合流します）。

1. パーツ置き場から盤面へドラッグして離す（幼児の主操作）
2. パーツ置き場をタップして選び、盤面のマスをタップする（PC・タップ操作の補助）

ドラッグ中は、置ける位置にだけ薄い下書き（ghost）を出します。置けない位置では何も出さないことが
そのまま「ここには置けない」の合図になります。置けなかったときは `role="status"` で
「ここには おけないよ」と伝え、盤面は変えません。

## 6. UIと物理処理の分離

- Reactが持つ状態は `puzzleState.ts` の `PuzzleState`（`phase` / `parts` / `runId`）だけです。
  物理Bodyは `usePuzzleEngine` の中だけに存在します。
- 進行は `edit`（配置）→ `running`（実行）→ `cleared`（ゴール）の3状態です。
  状態遷移はすべて純粋関数（`startRun` / `reachGoal` / `returnBall` / `clearAll`）で、
  実行中は `tryPlacePart` が `null` を返すため、配置と実行が混ざりません。
- `runId` は実行の世代です。「ボールをおとす」たびに増え、エンジンはこの値の変化で
  物理世界を作り直します。前回の実行の速度や位置が次へ持ち越されないことを構造で保証しています。
- ボールの描画は、毎フレームDOM要素へ直接 `transform` を書き込みます（Reactの再レンダーを経由しない）。
- ゴール判定は `goal.ts` の `isInGoalArea(x, y)` です。センサーBodyではなく座標判定にしてあるため、
  物理エンジンを動かさずに単体テストできます。

Phase 2で「途中停止して、その位置のまま編集へ戻る」を足すときは、`PuzzlePhase` に停止状態を
加え、ボールの位置を `PuzzleState` へ持たせて、エンジンがその位置から再開する形になります。
Phase 1では、その情報はまだ持ちません。

## 7. 国旗ボール

`src/components/flag-ball/`（こっきピンボール・こっきコロコロぼうけんと共通）の
`FlagBall` と `flagBalls` をそのまま使います。Phase 1では国旗を選ぶ画面を作らず、
`BALL_FLAG_ID = 'jp'` を固定で使います。選べるようにするときは、こっきドミノや
こっきピンボールと同じ選択画面の作りを足します。

## 8. 物理パラメータ

`puzzlePhysics.ts` に集約しています（UI側からは触りません）。

- 固定タイムステップ 60fps（端末のフレームレートで挙動が変わらないようにする）
- 重力 `y: 0.6`（680pxの盤面で、板に当たった向きの変化が目で追える速さ）
- ボールは弾みより転がりを優先（`restitution: 0.28`、`friction: 0.02`）
- 速度・角速度のクランプ（薄い板のすり抜けと、国旗が読めないほどの回転を防ぐ）
- 外周壁（左・右・床）を盤面の外側に置き、盤外へ逸脱させない

## 9. テスト

UI操作に依存しないロジックは単体テストしています。

| ファイル | 内容 |
| --- | --- |
| `grid.test.ts` | グリッド座標変換、スナップ、グリッド内外の判定 |
| `partTypes.test.ts` | パーツ定義の整合性（IDの重複、形が占有マスに収まること） |
| `placement.test.ts` | 占有判定、重複配置拒否、ボード外配置拒否、ポインタ座標の逆変換 |
| `goal.test.ts` | ゴール判定と、ゴールが開始位置の真下から外れていること |
| `puzzleState.test.ts` | 進行状態の遷移、実行中は配置できないこと |
| `FlagRollPuzzlePlay.test.tsx` | 画面全体（ドラッグ配置・タップ配置・重なり拒否・実行・ゴール・リセット） |

画面テストでは matter-js を動かさず、`usePuzzleEngine` を差し替えてゴールを直接起こします
（こっきピンボールの `FlagPinball.test.tsx` と同じ方針）。
