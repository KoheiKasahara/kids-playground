# いろぬりパズル 設計（Phase 1 / Phase 2 / Phase 3）

## 目的・対象年齢

2〜5歳が説明なしで「色を選ぶ → エリアをタップ → 一気に塗られる」体験だけで遊べる、幼児向けのぬりえミニゲームです。線からはみ出す心配がない領域単位の塗りつぶし方式を採用し、失敗や正誤判定を持ちません。

## URLと画面遷移

難易度選択や結果画面を持たず、単一URLで完結します。Phase 2 の完成演出も別ページではなく、同じ画面のフェーズ切り替えとして実装しています（絵と塗り状態をそのまま使い続けるため）。

| 画面 | URL |
| --- | --- |
| プレイ（唯一の画面） | `/games/color-paint-puzzle` |

```text
ホーム → いろぬりパズル（題材をえらぶ・いろをえらぶ・ぬる・やりなおし）
          → 「できた！」→ 完成演出（絵が動く）→ 「もういちどぬる」→ ぬりえへ戻る
```

SVGのみに依存し軽量なため、他の3D/物理演算ゲームと違って遅延読込（`React.lazy`）にはせず、静的importで`routes.tsx`に登録しています。

## 題材とエリア

題材は6種類（`くるま` / `さかな` / `ちょうちょ` / `ロボット` / `ロケット` / `きょうりゅう`）で、既定は `くるま` です。すべて `viewBox="0 0 100 100"` の座標系で定義します。

| 題材 | id | 塗れるエリア |
| --- | --- | --- |
| くるま | `car` | そら / じめん / くるまの ボディ / やね / まど / ライト / うしろの タイヤ / まえの タイヤ |
| さかな | `fish` | みず / さかなの からだ / おびれ / せびれ / はらびれ / おおきな あわ / ちいさな あわ |
| ちょうちょ | `butterfly` | そら / ひだりの うえばね / みぎの うえばね / ひだりの したばね / みぎの したばね / からだ |
| ロボット | `robot` | そら / じめん / ひだりの うで / みぎの うで / ひだりの あし / みぎの あし / ロボットの からだ / あたま / かお / むねの ボタン |
| ロケット | `rocket` | そら / ひだりの はね / みぎの はね / ほのお / ロケットの ボディ / せんたん / まど |
| きょうりゅう | `dinosaur` | そら / じめん / しっぽ / うしろの あし / まえの あし / せなかの トゲ / きょうりゅうの からだ / おなか / あたま |

エリア数は幼児が塗り切れる範囲に収めるため、1題材あたり10件以下を上限としてテストで固定しています（背景を含む）。

追加した3題材も、既存3題材と同じ作り方（太い黒の輪郭・単純な形・重なりで付け根を隠す）に揃えています。あし・うで・はね・しっぽ・せなかのトゲのように「本体から生えている」エリアは、必ず**本体より先に**（＝奥に）描いて付け根を本体の塗りで隠します。本体の上に描くと、塗りの内側に浮いた四角や線として見えてしまいます。

目・ホイールの中心・もよう・しょっかく・ロボットのアンテナ・ロケットのほしなどの装飾は塗れない`details`として別データに持たせ、`areas`（塗り対象）とは型・配列ともに分離しています。

くるまの「まど」・ロボットの「かお」・ロケットの「まど」・きょうりゅうの「おなか」のように、大きなエリアの内側に入れ子にする塗りエリアは、外側にも塗れる幅が十分残る大きさにとどめます（内側を大きく取りすぎると、外側が細い枠だけになって幼児には押しにくくなります）。

## 塗りつぶし方式（SVGエリア単位・塗り／輪郭／装飾の分離）

`ColoringCanvas.tsx` は同じ題材データを役割ごとに描き分けることで、「塗りが輪郭を崩さない」ことを構造で保証します。

1. **塗り＋輪郭（エリアごとに交互）**: `areas` を配列順（先頭が最背面）に、「塗り（fillのみ）」→「輪郭（同じshapeを`fill="none"`＋太い黒のstrokeで重ねる、`pointer-events: none`）」の順で1エリアずつ描画します。自分の塗りが自分の輪郭を覆うことはなく、かつ後ろのエリア（例: タイヤ）が手前に重なるときは前のエリアの輪郭が正しく隠れます。輪郭を全エリアぶんまとめて最前面に描くと、タイヤの上をボディや地面の線が横切ってしまいます。
2. 塗り図形が、実際にタップ可能な要素そのものです。`role="button"` / `tabIndex={0}` / `aria-label`（読み上げ用の日本語ラベル）を持ち、クリックとキーボード（Enter・Space）の両方で発火します。fillは塗られていれば選択色のhex、未塗りなら`UNPAINTED_FILL`です。
3. **装飾レイヤー**: `details`（目・ホイールの中心・もよう・まどのガラス等）を最前面に描画します。`pointer-events: none` / `aria-hidden="true"` なので、タップは必ず下の塗りエリアに届きます。

図形は `path`（絶対座標のM/L/C/Q/Zのみ）/ `circle` / `ellipse` の3種類のみで表現し、`shapeBounds.ts` が全図形からタップ領域サイズ検証用のバウンディングボックスを計算します。

## 状態管理

- 色は `PaintColorId`（例: `'red'`）で保持し、hexは表示直前に`findPaintColor`で引きます。Phase 2で「塗った色のまま絵を動かす」再利用をしやすくするための設計です。
- 塗り状態は `pictureId -> areaId -> colorId` の2段マップ（`PaintingsState`）で、`paintState.ts`のすべての関数は非破壊（引数を変更せず新しいオブジェクトを返す）です。
- 題材を切り替えても、それぞれの絵の塗り状態は保持されます。「やりなおし」は表示中の絵だけを初期状態に戻します。

## タップ領域の考え方

`MIN_TAP_SIZE_UNITS`（16単位）を、viewBox幅100単位に対して最小想定キャンバス幅300pxを仮定したときの約48px（規約の補助操作44px以上を満たす目安）として定義し、全題材の全エリアがこの最小サイズ以上のバウンディングボックスを持つことをテストで検証します。

path（ベジェ曲線）のbboxは、実曲線ではなく制御点まで含めた外接矩形（過大評価）で近似しています。実曲線は制御点の凸包に収まるため、この近似は「タップ領域が実サイズ以上であること」の検証には安全な向きの誤差です。

bboxのテストだけでは「他のエリアに上から重ねられて、実際に押せる範囲が細くなっていないか」までは分からないため、実画面（Playwright）で各エリアの実タップ点をヒットテストし、狙ったエリアが塗られることを確認しています（iPhone 12相当390x844 / 狭い縦画面320x568 / 横画面740x360）。

## 画面レイアウトで気をつけている点

- ぬりえのSVGは1:1のアスペクト比を持つため、通常フローに置くと「与えられた幅ぶんの高さ」または「高さぶんの幅」を要求してレイアウトを押し広げます。カード側を`position: relative`、SVG側を`position: absolute` ＋ 実寸の`width`/`height`にして、大きさをグリッドの行と列だけで決めています（SVGは置換要素なので、`width`/`height`を`auto`にすると`inset`ではなく固有アスペクト比で大きさが決まる点にも注意）。
- ページのグリッドは`grid-template-columns: minmax(0, 1fr)`を明示し、横スクロールが出ないようにしています。
- 色パレットと題材えらびはどちらも列数を固定し（色: 狭い縦画面4列 / 560px以上8列 / 横画面3列、題材: 狭い縦画面3列×2段 / 620px以上6列×1段）、幅によって4+2のようなはんぱな折返しが起きないようにしています。題材だけ6列への切り替えを色パレット（560px）より広い620pxにしているのは、いちばん長い「きょうりゅう」が1行で収まる列幅（およそ96px）を確保するためです。
- 低い横画面では、題材えらび（6件）を左の操作列（27%幅）に入れると1つ62px程度になり「きょうりゅう」が収まらないため、題材えらびだけ全幅の1段に出して6件を1行に並べています。左の操作列（色・やりなおし・できた！）の高さは変わらないので、この配置でページ全体は縦に伸びません。
- タップでもフォーカスリングが出るとエリアの周りに枠が残って見えるため、ポインタ操作のときだけフォーカスを外し、キーボード操作のフォーカスリングは残しています。

## Phase 2: 「できた！」と完成演出

### フェーズ

画面は `coloring`（いつも通り塗れる） / `celebrating`（完成演出中）の2状態だけで、`paintPhase.ts` の純粋な遷移関数 `reducePaintPhase` が持ちます。ライブラリは追加していません。

| いま | 操作 | つぎ |
| --- | --- | --- |
| `coloring` | 「できた！」 | `celebrating` |
| `celebrating` | 「できた！」 | `celebrating`（無視する） |
| `celebrating` | 「もういちどぬる」 | `coloring` |

`celebrating` 中の `finish` は**同じ値をそのまま返す**ため、Reactが再レンダリングせず、連打しても演出が作り直されません（＝多重起動しない）。塗り操作は `canPaint(phase)` で、`ColoringCanvas`（ハンドラを付けない）と画面側（状態更新を弾く）の両方で止めています。

タイマーは一切使っていません。演出はCSSアニメーションだけで動き、終わるのは子どもが「もういちどぬる」を押したときだけです。時間で勝手に終わらせないのは、(1) 見ている途中で取り上げない、(2) タイマーとリセット・題材切り替えの競合をそもそも作らない、の2つの理由からです。

### 「できた！」ボタン

- 塗り具合を一切見ません。何も塗っていなくても、一部だけでも、全部塗っても同じように押せます（完成を決めるのはシステムではなく子ども）。
- 高さ68px以上・角丸・暖色グラデーション＋テキストで、平らな色のマスに `✓` が付くだけの色パレットとは形も質感も明確に変えています。
- やりなおしと同じ行に、やりなおしを小さく・「できた！」を大きく置いて優先順位を示します。

### 完成演出（同じ画面のまま切り替える）

別ページへ遷移せず、**Phase 1 と同じ `ColoringCanvas`・同じ塗り状態 `PaintingsState` をそのまま描き続けます**。演出用の別データや固定色の完成画像は持ちません。これが「ユーザーが塗った色のまま動く」ことの保証で、色が失われる余地が構造上ありません。

演出中は題材えらび・色パレット・やりなおしを出さず、タイトルを薄くして絵を主役にします。ホームへの「もどる」だけは、いつでも抜けられるよう残します。押した瞬間はカードが軽く弾み（`cardPop`）、キラキラが1回だけ飛んで消え、`playColorPaintFinishSound()` が短い上行の完成音を鳴らします。

### 絵の動かし方（`motion` と `<g>` の2階層）

題材データの各 `area` / `detail` は、任意で `motion: { group?, part? }` を持ちます。`ColoringCanvas` は `motionTree.ts` の `buildMotionTree` でこの指定に従い、描画順を保ったまま `<g data-motion-group>` → `<g data-motion-part>` の2階層にまとめます。`<g>` はフェーズによらず常に同じ構造で描くので、演出の開始・終了でSVGが作り直されず、塗りが一瞬消えることがありません。

動きはCSS（`ColoringCanvas.module.css`）が `data-phase='celebrating'` のときだけ、この data 属性に対して与えます。動かすのは `transform` と `opacity` だけで、`fill`（＝ユーザーの色）には一切触れません。

- `group` 未指定 = 背景（そら・みず・じめん）。動かず、絵だけが動きます。
- 回転・拡大の中心は、`group` が `transform-box: view-box`（viewBoxの中心 50,50）、`part` が `transform-box: fill-box`（その図形自身の中心）が既定です。例外は2つで、地面に立つ題材（くるま `50% 84%` / ロボット `50% 89%` / きょうりゅう `50% 86%`）は接地面を中心にし（絵の中心で縮めると足が地面から浮く）、ちょうちょの羽はからだの軸で畳みたいので `view-box` に戻します。
- 左右のタイヤのように回転中心が違うものは、必ず別の `part` にします（同じにすると2つの合成bboxの中心＝車体の真ん中を軸に回ってしまう）。この不変条件は `paintPictures.test.ts` で検証しています。

| 題材 | 動き |
| --- | --- |
| くるま | タイヤが回る（`carWheel`）／少し下がって「ため」を作り、右へ走って跳ね、戻ってくる（`carDrive`）。タイヤの回転は `carDrive` と同じ長さ・同じ遅延にして、進行方向と回転方向を合わせている |
| さかな | おびれを付け根から振る（`finWag`）／はらびれを控えめに揺らす（`finWagSmall`）／ゆらゆら泳ぐ（`fishSwim`）／あわは魚と別に、その場で上へのぼって消える（`bubbleRise`） |
| ちょうちょ | 左右の羽をからだの軸へ畳む＝羽ばたき（`wingFlap`）／ふわふわ飛ぶ（`butterflyFly`） |
| ロボット | 左右のうでをかたを軸に逆向きに振る（`robotArmSwing` / `robotArmSwingBack`）／その場でぴょこぴょこ足ぶみする（`robotStep`）／アンテナの玉だけその場で光る（`robotAntennaBlink`） |
| ロケット | ほのおが付け根を軸に伸び縮みしてゆらぐ（`rocketFlameFlicker`）／ふわりと打ち上がって戻る（`rocketFly`）／ほしはロケットと一緒に飛ばず、そらで明るさだけ変える（`starTwinkle`） |
| きょうりゅう | しっぽを付け根から振る（`dinoTailWag`）／くびの付け根を軸にあたまをうなずかせる（`dinoHeadNod`）／のっしのっしと歩く（`dinoWalk`） |

いずれも `<題材>Enter`（押した瞬間に一度ポンッと大きくしてから、走る・泳ぐ余白を作るために少しだけ小さく収める）→ 遅延付きのループ本体、という2本立てです。ループ側の0%を `Enter` の100%と同じ `scale` にしてあるので、繋ぎ目で跳ねません。

真円のタイヤは回しても見た目が変わらないため、Phase 2 で各タイヤに放射状のスポーク（塗れない `detail`）を足しています。ぬりえ中もホイールらしく見えるので、Phase 1 の見た目を損ないません。

`prefers-reduced-motion: reduce` では、走る・泳ぐ・羽ばたく・キラキラの動きを止め、ゆっくりした拡大（`calmBreath`）だけ残します。

### 演出後の導線

「もういちどぬる」は**塗り状態を一切触らずに** `coloring` へ戻すだけです。`resetPicture` は呼びません。色を少し変えてもう一度動かす遊びがそのままできます。題材の切り替えは Phase 1 の題材ボタンで従来どおり行えます。

### Phase 2 の非目標

お手本・正誤判定、スコア、保存・シェア、高度なステージ選択、大規模な音演出、物理演算、共通ぬりえ基盤への大規模リファクタは実装しません（Phase 4: UI/UX・音・最終仕上げ）。

## Phase 3: 題材の追加（ロボット・ロケット・きょうりゅう）

「えらぶ楽しさ」を増やすため、Phase 2 の3題材に ロボット / ロケット / きょうりゅう を足して6題材にしました。データ構造・描画・演出の仕組みは Phase 2 のままで、`paintPictures.ts` に3件のデータ、`ColoringCanvas.module.css` に3件ぶんのアニメーションを足しただけです（新しい概念・新しいコンポーネントは追加していません）。

題材選びの基準は「幼児が見てすぐ分かる形」「エリアが細かくなりすぎない」「既存3題材と並べて浮かない太い線と単純な形」の3つです。ステージ選択やロック解除は導入せず、既存の上部タブに6件を並べるだけにとどめています（遊び方を変えないため）。

くるま・ロボット・きょうりゅうは同じ地面（`GROUND_PATH`）を共有します。もともとくるま専用だった座標をそのまま定数に切り出したもので、見た目は変わりません。
