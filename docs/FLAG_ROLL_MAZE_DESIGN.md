# 「こっきころころめいろ」基本設計

## 概要とこの文書の範囲

「こっきころころめいろ」は、スマートフォン・タブレット・PCで盤面を傾け、ボールを3D迷路のゴールまで転がすミニゲームです。対象は幼児（4〜5歳を想定）で、正誤やスコアを競うクイズではなく、「盤面を傾けてボールを転がす操作そのものが楽しいか」を確かめるための最小構成です。

この文書はPhase 5までの実装（複数ステージ、バーチャルスティック／ジャイロ操作、国旗ボール、追従カメラ、3Dステージギミック）を扱います。ミニゲーム開発規約（`docs/MINIGAME_DEVELOPMENT_GUIDELINES.md`）§9はクイズ系ゲームの設計書を主に想定しており、このゲームはクイズではないため、問題数・選択肢数・むずかしさの累積包含に関する項目は対象外です。かわりに、入力の抽象化、物理構成、ステージを増やしても詰まらないための仕組みを中心に記載します。

## URLと画面遷移

```text
/games/flag-roll-maze        国旗 → ステージ選択
/games/flag-roll-maze/play   プレイ
```

`src/app/routes.tsx` に `lazyRoute` で登録し、Three.jsとRapierを含むこの画面は遅延読み込みします。ホームの「こっきころころめいろ」カードから入り、画面下の「もどる」ボタンで `/` へ戻ります。

`/games/flag-roll-maze`は、同じ画面内で国旗を選ぶ`flag`ステップとステージを選ぶ`stage`ステップを切り替える2段階の選択画面です。画面を増やさず、`FlagRollMazeSelect.tsx`の`step` stateで切り替えるため、国旗を選んだあとに戻っても選択を保持できます。プレイ画面へは`location.state`で`{ flagId, stageId }`を渡し、`playState.ts`が国旗IDとカタログにあるステージIDだけを受け付けます。ルート自体はPhase 4から増やしていません。

ゴール後の状態も同じプレイ画面の`gameState`で表現します。「もういちど」は同じステージをやり直し、カタログの最後以外では「つぎの ステージ」で次のIDへ進めます。ステージIDの変更は`useMazeEngine`の既存の解放・再生成経路を使うため、画面を遷移し直さずに物理世界とThree.jsシーンを安全に作り替えます。

## 入力の抽象化

このゲームの設計の核は、「操作デバイス」と「盤面物理」を`TiltInput`という共通の型で分離していることです。

```ts
// src/games/flag-roll-maze/tiltInput.ts
export type TiltInput = {
  x: number
  y: number
}
```

`x` は盤面のワールド+X方向、`y` は盤面のワールド+Z方向へ「下り坂を作る」量を表します。画面上はカメラが+Z側から見下ろすため、`y`が正だと手前（画面下）へ転がります。大きさ（`x`,`y`のノルム）は常に0〜1に正規化され、1が最大の傾きです。

データの流れは一方向です。

```text
バーチャルスティック / 矢印キー・WASD
        ↓（デバイス固有の値をTiltInputへ変換）
      TiltInput
        ↓ gravityFromTilt()
      重力ベクトル
        ↓ Rapierの world.gravity
       物理演算
```

Phase 2でスマートフォンのジャイロ（Device Orientation）を足すときは、「センサー値 → TiltInput」の変換をもう1つ追加するだけで済み、`mazePhysics.ts` や `mazeWorld.ts` などの物理側は変更不要です。`useMazeEngine`は`setTilt(tilt: TiltInput)`しか受け取らず、入力の出どころ（マウスなのかタッチなのか、将来ジャイロなのか）を知りません。

各責務は次の関数に分かれています。

- デッドゾーン: `applyTiltDeadzone`（`tiltInput.ts`）。しきい値`TILT_DEADZONE = 0.18`の内側を中立にし、境界のすぐ外は0付近から力が立ち上がるよう再スケールする。単純な切り捨てだと境界で急に力が立ち上がるため。
- クランプ: `clampTiltMagnitude`（`tiltInput.ts`）。ノルムが1を超えたら方向を保ったまま1へ丸める。バーチャルスティックの半径超え、キー同時押しの合成の両方で使う。
- 平滑化: `smoothTilt` / `tiltDampFactor`（`tiltInput.ts`）。指数減衰で現在値を目標値へ毎フレーム寄せる。減衰係数は`TILT_SMOOTHING_LAMBDA = 9`（1/秒）で、フレーム落ちしても経過時間から補間係数を再計算するので手触りが変わらない。この処理は`useMazeEngine`の`tick`内で毎フレーム呼ばれ、入力が飛んでも重力が階段状に切り替わらないようにしている。

バーチャルスティックの入力は`tiltFromStickOffset(offsetX, offsetY, radius)`でドラッグ量(px)を`TiltInput`へ変換し、半径を超えて引いても1で頭打ちにします。矢印キー／WASDは`tiltFromPressedKeys`で同時押しを合成してから正規化するため、斜め押しが直線より速くなりません。

## 3D・物理構成

描画にはThree.js（生のAPI）、物理にはRapier 3D（`@dimforge/rapier3d-compat`）を使います。同じRapier wasmは`domino-flag`（こっきドミノ）の`useDominoEngine.ts`と共有しており、新規にwasmを追加していません。

盤面の傾きは、床・壁のコライダーを毎フレーム動かすのではなく、**入力から重力ベクトルの向きを変える**ことで表現します（`mazeWorld.ts`の`applyTiltToGravity`が`world.gravity`を書き換える）。理由は次の2つです。

- 固定コライダーを毎フレーム動かすとRapier側の再計算コストが増え、低速端末で不利になる。
- Phase 2でジャイロ入力を足すときも、`TiltInput`から重力を作る`gravityFromTilt`だけを差し替えればよく、コライダーの姿勢管理を新たに作らずに済む。

重力ベクトルへの変換は次の式です（`mazePhysics.ts`の`gravityFromTilt`）。入力の大きさ`m`（0〜1）から傾き角`θ = m · MAX_TILT_RAD`を求め、大きさが常に`GRAVITY_MAGNITUDE`のまま、水平成分`sinθ`・垂直成分`-cosθ`へ向きだけを変えます。傾けても重力の総量は変わりません。

見た目の盤面（`boardGroup`）は物理と同じ向きへ、角度だけ`VISUAL_TILT_RATIO = 0.62`倍浅く回します（`visualTiltRotation`）。物理の傾きをそのまま見せると画面の傾きが大きすぎて酔いやすいため、見た目は控えめにしつつ、どちらへ転がしているかは分かる程度の手応えを残しています。

回転軸の符号には注意が必要です。傾けた平面の下り坂の向きは、**法線が倒れる向きと同じ**になります（高さが `y = -(nx·x + nz·z)/ny` なので、最急降下方向は法線の水平成分 `(nx, nz)`）。したがって入力方向へボールを転がすには、法線を入力と同じ向きへ倒す軸 `(uz, 0, -ux)` を使います。符号を逆にすると、ボールが「持ち上がった側の端」へ転がる＝上り坂を登るように見えてしまいます。`mazePhysics.test.ts`は、見た目の下り坂の向きが重力の水平成分と一致することを直接検証してこれを防いでいます。

物理は固定タイムステップ`PHYSICS_TIMESTEP = 1/120`秒で積分し、1フレームあたり最大`MAX_PHYSICS_SUBSTEPS = 4`回まで進めます（`useMazeEngine.ts`の`stepPhysics`）。表示は60Hz想定でも、接触判定を薄いコライダーがすり抜けないよう物理は120Hzで刻み、低速端末で追いつけないときは溜まった時間を捨てて次のフレームから作り直します。タブ復帰時などの巨大な時間跳躍は`MAX_FRAME_DELTA_MS = 100`msで頭打ちにしてから物理へ渡します。

床・壁・バンパーは固定コライダー（親`RigidBody`を持たない`Collider`）です。動的剛体はボール1個、回転棒は置いた本数ぶんのkinematic position based剛体で、バンパーのために剛体を増やしていません。ボールは連続衝突判定（CCD）を有効にし、傾きを止めたままsleepさせない設定にして、次の入力への反応が遅れないようにしています（`mazeWorld.ts`の`createMazeWorld`）。具体的な個数は「パフォーマンス」の節で、`mazeWorld.test.ts`の性能ガードと合わせて示します。

## 3Dギミックの物理方式

### 回転する棒

回転棒は`RigidBodyDesc.kinematicPositionBased()`で作ったkinematic position basedの剛体に、`ColliderDesc.cuboid`の直方体コライダーを1つ付けています。物理ステップの前に`advanceSpinners`が`setNextKinematicRotation`へ次の姿勢を渡します。kinematic剛体を`setRotation`で直接動かすと、Rapierから見た接触速度が0になり、棒がボールを押せません。次の姿勢を`setNextKinematicRotation`で設定することで、移動に伴う接触速度が物理へ伝わります。

既定の寸法は長さ`SPINNER_LENGTH = 2.4`、厚み`SPINNER_THICKNESS = 0.26`、高さ`SPINNER_HEIGHT = 1.15`です。棒を長くして通路を完全に塞ぐのではなく、ボールが回避できる余白を残す寸法にしています。

角度は`spinnerAngleAt`で、`initialAngle + angularSpeed * elapsedSeconds`として経過時間から直接求めます。前フレームの角度へ毎回加算する方式にしないため、処理落ちやフレーム数の違いで回転誤差が蓄積しません。`resolveGimmicks`が掃引円の半径を`Math.hypot(length / 2, SPINNER_THICKNESS / 2)`で求め、配置検証とスタック脱出の基準を同じにしています。`useMazeEngine`では固定タイムステップの`PHYSICS_TIMESTEP`ごとに`physicsElapsedSeconds`を進め、その値からステージに置かれた回転棒を更新してから`world.step()`を呼びます。

### バンパー

バンパーは親剛体を持たない固定の`ColliderDesc.cylinder`です。固定物として置くことで、見た目のバンパーごとに剛体を追加せずに済みます。接触後、`applyBumperKicks`がボールとバンパーの水平距離を確認し、バンパー中心から外向きの一定インパルス（`BUMPER_KICK_IMPULSE`）を加えます。コライダーの反発（`BUMPER_RESTITUTION`）だけでは低速で「ポン！」と見えないため、速度に依存しないキックを重ねています。

同じバンパーが接触中に毎ステップ発火すると連打のようになるため、`canKickBumper`と`markBumperKicked`でIDごとの時刻を管理し、`BUMPER_COOLDOWN_MS = 260`msの間は再発火させません。既定の半径は`BUMPER_RADIUS = 0.46`、高さは`BUMPER_HEIGHT = 0.9`、一定キックは`BUMPER_KICK_IMPULSE = 2.4`、接触範囲へ加える余白は`BUMPER_KICK_MARGIN = 0.04`です。キック後には速度上限ももう一度適用し、弾みが操作不能な速さへ膨らまないようにしています。

### 穴

床を盤面全体の1枚板にすると穴へ落ちられないため、`createMazeWorld`は`stage.floors`の矩形ごとに固定コライダーを作ります。`buildFloorRects`は`O`のマスを床に含めず、残りのマスをまず行ごとに横方向の連続区間へまとめ、その後、同じ列範囲が続く区間だけを縦方向へ貪欲にマージします。横→縦の順でまとめることで、穴を抜いたまま床矩形の枚数を抑えています。

穴は`O`のマスごとに1件の`MazeHole`として解決されます。たとえば、ぼうけんステージには3件、あなあなステージには12件あります。床コライダーは穴のマスに置かず、表示上は穴のリングと、判定位置より下のピットを置くため、ボールは実際に下へ抜けて`HOLE_FALL_Y`で落下と判定されます。

## パフォーマンス

動的剛体は各ステージのボール1個だけです。回転棒は本数ぶんのkinematic position based剛体として数え、バンパーは親剛体を持たない固定コライダーなので剛体数を増やしません。選択中のステージだけをRapierとThree.jsへ生成し、ほかの4ステージを同時に組み立てることはありません。

`mazeWorld.test.ts`の性能ガードは、全ステージについて実際にワールドを組み立て、`world.bodies.len()`と`world.colliders.len()`を確認してから必ず`free()`します。実測値と上限は次の通りです。

| ステージ | 剛体 | コライダー |
| --- | ---: | ---: |
| kantan | 1 | 18 |
| kurukuru | 3 | 27 |
| ponpon | 1 | 22 |
| anaana | 1 | 38 |
| adventure | 3 | 30 |

各ワールドは、`剛体 = 1 + 回転棒数`、`コライダー = 床矩形数 + 壁矩形数 + 回転棒数 + バンパー数 + ボール1個`という内訳も検証します。上限はステージごとに剛体6以下・コライダー80以下です。床を穴ごとに細かく分割せず`buildFloorRects`で横→縦へまとめ、壁を横長にまとめるのは、この上限内で遊びの違いを作るためです。

## カメラ

斜め上からボールを追いかけるカメラです（`mazeCamera.ts`）。仰角は`CAMERA_ELEVATION_RAD`（58°）、視野角`CAMERA_FOV`は50°で、**向きと仰角は一切変えず、位置だけがボールへ追従します**。方向が変わらないので、追いかけていても「どちらが画面の奥か」が分からなくなりません。

カメラの距離・追従・ズームはPhase 3から変更していません。Phase 4のギミックや落下復帰、Phase 5のステージ切り替えでも、既存のカメラ追従と復帰直後のスナップを使います。ステージごとのカメラ設定は持ちません。

Phase 1〜2は盤面の四隅がすべて画角へ収まる距離を解く固定カメラでした。しかしこの方式では、ステージが大きいほどカメラが遠ざかるため、国旗ボールが小さくなり「何の国旗を転がしているか」が分かりません（幅390pxのスマホで直径25px）。Phase 3の仕上げで、この「全景を1画面へ収める」制約を撤廃しました。

### 距離は盤面ではなく「ボールの画面占有率」から決める

`computeMazeCameraDistance(aspect)`は、次の3つの条件をそれぞれ距離へ変換し、最も遠いものを採用します。**boundsの大きさを見ないので、コースを長くしてもカメラの寄りは変わりません。**

そのため、幅広いぽんぽん、縦長のあなあな、中央を回り込むくるくるでも、盤面サイズや縦横比に応じて自動で引きすぎることはありません。国旗ボールを同じ大きさで見せることを優先し、どのステージも同じ計算とズーム段を使います。

| 条件 | 定数 | 意図 |
| --- | --- | --- |
| ボールが画面短辺に占める割合 | `BALL_SCREEN_DIAMETER_RATIO = 0.173` | 幅390pxのスマホで直径約67px、国旗パネル幅約42px |
| 標準距離で画面短辺に残すマス数 | `MIN_VISIBLE_CELLS_ON_SHORT_SIDE = 3.0` | 寄りすぎて進行方向の通路が見えなくならないための歯止め |
| 絶対的な最短距離 | `MIN_CAMERA_DISTANCE = 3` | near面へ入り込ませない |

**この2つは1つのつまみです。** カメラを引けば見える範囲が広がり、同じ比率でボールが小さくなります。実機確認を2回行い、いずれも「国旗は十分読める。曲がり角の先をもっと見たい」という同じ向きの結果だったため、占有率を 0.22 → 0.19 → 0.173 と段階的に下げました。初期値0.22からは見える範囲が約27%広がり（短辺 3.03マス → 3.85マス）、ボールは約21%小さくなっています（幅390pxのスマホで直径86px → 67px）。

国旗パネル幅42pxは、`FlagBall`の円形クロップが「模様を見分けられる大きさ」として採用している48pxを下回ります。ただしパネルは円形に切らず4:3のまま枠線付きで見せるため、同じ画素数でも国旗として読みやすく、実機で判別できることを確認しています。迷路の見通しと国旗の読みやすさはこの1つの定数のトレードオフなので、今後の調整もここだけで済みます。

短辺の半画角は`tan(FOV/2) · min(1, aspect)`で、縦画面では横幅、横画面では高さが短辺になります。この1本の式で縦横どちらも解けるので、リサイズのたびに呼び直すだけで済みます。

### 注視点の追従

毎フレーム、次の順で注視点（水平2成分）を更新します。高さは`BALL_RADIUS`固定で、ボールが跳ねても画面が上下に揺れません。

1. **先読み**: `desiredCameraFocus`が、ボール位置へ速度の水平成分×`LOOK_AHEAD_SECONDS = 0.32`を足します。先読み量は`MAX_LOOK_AHEAD_IN_RADII = 2.4`（球半径の2.4倍）で頭打ちにし、ボールを画面端へ追いやりません。これで進行方向が少し多く見えます。
2. **クランプ**: 外周1マスぶん内側の「歩ける矩形」へ収め、壁の外側を映しすぎないようにします。inset（既定は`CELL_SIZE`）は引数で差し替えられます。
3. **補間**: `followCameraFocus`が`CAMERA_FOLLOW_LAMBDA = 5.0`（1/秒）の指数減衰で寄せます。経過時間から係数を再計算するので、30fpsでも60fpsでも同じ時間で収束し、急な追従で画面酔いしません。
4. **リーシュ**: 補間後の注視点が（先読みを含まない）ボール位置から`MAX_FOLLOW_LAG_IN_RADII = 3.0`（球半径の3倍）より離れたら、遅れの向きを保ったままその距離へ引き戻します。**カメラが物理ボールへ追いつけなくなることが構造的に起きません。**

生成直後・「スタートに もどる」・場外復帰・「もういちど」では注視点をボール位置へ即座にスナップさせ、カメラがスーッと飛んでいく演出になるのを防いでいます。

### プレイ中に距離だけを変えられる「＋ / −」

端末の大きさや持ち方によって「もう少し引いて迷路の先を見たい」「もう少し寄って国旗ボールを大きく見たい」の好みが分かれるため、プレイ画面の3Dシーン右下に `＋` / `−` の2ボタンを置いています。UIは既存の「ちきゅうぎ」（`src/games/earth-globe/ui/ZoomControls.tsx`）に合わせ、円形・同じ文言（`もっと ちかづく` / `もっと はなれる`）・端で `disabled` にする形を踏襲しました。コードは共通化していません（片方は地球の周回カメラ、もう片方は追従カメラで、変える対象も範囲も別々のため）。

ズームは **標準のカメラ距離へ掛ける倍率** としてだけ効きます。注視点の追従・カメラの向き・仰角・入力・物理には一切触れません。

| 段 | 倍率 | ボールの画面占有率 | 短辺に入るマス数 | 国旗パネル幅(幅390px) |
| ---: | ---: | ---: | ---: | ---: |
| 0（一番引く） | 1.39 | 12.4% | 5.35マス | 30px |
| 1 | 1.29 | 13.4% | 4.97マス | 33px |
| 2 | 1.19 | 14.5% | 4.58マス | 35px |
| 3 | 1.09 | 15.9% | 4.20マス | 39px |
| **4（標準）** | **1.00** | **17.3%** | **3.85マス** | **42px** |
| 5 | 0.92 | 18.8% | 3.54マス | 46px |
| 6 | 0.84 | 20.6% | 3.23マス | 50px |
| 7 | 0.77 | 22.5% | 2.96マス | 55px |
| 8（一番寄る） | 0.71 | 24.4% | 2.73マス | 59px |

1段あたり8〜9%と小さいので、数回押して好みの距離に合わせられます。一番引いても短辺に入るのは約5.4マスで、11×11のステージ全体は見渡せません。一番寄せる段はボールを画面短辺の24.4%まで大きくするため、細かい仕掛けを確認したいときの選択肢にしています。

段を切り替えたときは `followZoomScale` が指数減衰（`CAMERA_ZOOM_LAMBDA = 8`）で倍率を埋めるので、距離が跳ねて画面が飛ぶことはありません。シーンの生成時だけはアニメーションさせず、選ばれている段の距離から始めます。

ズームの段はプレイ画面の`zoomIndex` stateと`useMazeEngine`内のrefで持ちます。React stateでボタンの有効・無効を表示しながら、`applyZoomIndex`でエンジンのズーム値へ反映します。`runId`でシーンを作り直すときだけでなく、`stageId`を変えて次のステージの物理世界を作り直すときも、選んだ段を引き継ぎます。**「スタートに もどる」「もういちど」「つぎの ステージ」ではズームを標準へ戻しません。** これらは救済・やり直し・連続プレイの操作で、見え方の好みまで巻き戻すと選び直す回数が増えるためです。国旗を選び直してプレイ画面へ入り直したときは、画面ごと作り直されるので標準の段から始まります。

### 見た目の傾きはボールを軸に掛ける

`boardGroup`の見た目の傾きは、以前はワールド原点まわりの回転でした。盤面の端にいるボールは最大傾き時に上下へ2ワールド単位ほど振れますが、全景固定カメラではそのぶんも画角に含めていたため問題になりませんでした。寄った追従カメラでは、これがそのまま画面の揺れになります。

そこで`visualTiltPivotOffset`（`mazePhysics.ts`）が「pivot点まわりの回転」にするための平行移動を求め、`boardGroup.position`へ与えます。回転中心をボールへ置くので、**ボールのワールド座標は物理座標と一致し**、カメラは物理座標だけを追えばよくなります。見た目上は「ボールを中心に盤面が傾く」ことになり、どちらへ転がしているかの手応えは変わりません。

### 今後のコースへの拡張

距離はステージの大きさに依存せず、注視点は`bounds`と現在位置だけから決まります。長いS字、一本道、分岐、大きな広場のようなコースを足しても、カメラ側の計算は変わりません。`mazeCamera.test.ts`は、幅3マス×長さ40マス相当の細長い`bounds`でも距離が変わらず、クランプが正しく効くことを確認しています。

## ステージ定義と盤面データ

ステージ固有のデータは`mazeStages.ts`、データから遊べる盤面を組み立てる共通処理は`mazeStage.ts`に分けます。`MazeStageDefinition`は次の形です。

```ts
export type MazeStageDefinition = {
  id: string
  nameJa: string
  emoji: string
  hintJa: string
  rows: readonly string[]
  gimmicks: readonly GimmickPlacement[]
  checkpointCells: readonly CellCoordinate[]
}
```

| フィールド | 意味 |
| --- | --- |
| `id` | 遷移stateとテストで使う、変わらない識別子 |
| `nameJa` | 選択画面とプレイ画面に出す短い名前 |
| `emoji` | 文字を読めない子も区別できる印 |
| `hintJa` | 名前だけでは違いが伝わらないための、ひらがなの短い説明 |
| `rows` | `#`=壁、`.`=床、`S`=スタート、`G`=ゴール、`O`=穴を表す文字グリッド |
| `gimmicks` | セル座標で書く回転棒・バンパーの配置 |
| `checkpointCells` | スタートから前進する順番で書く復帰先のセル座標 |

`mazeStage.ts`の`createMazeStage(rows, options)`は、文字グリッドから壁・床の矩形、穴、START/GOAL、チェックポイント、ギミックのワールド座標を組み立てます。空グリッド、行長の不一致、START/GOALの欠落もここで検証し、指定がなくても最初のチェックポイントをSTARTにします。`findMazePath`と`isMazeSolvable`は、この共通処理に属する経路の品質ゲートです。

`mazeStages.ts`は`MazeStageDefinition`のカタログ`MAZE_STAGES`と、そのデータから`createMazeStage`を呼ぶ薄い層です。依存は**`mazeStages.ts` → `mazeStage.ts`の一方向だけ**にし、ビルダーがカタログをimportしないため循環しません。主要な公開APIは次の通りです。

| API | 役割 |
| --- | --- |
| `createMazeStageById(id)` | IDに対応する定義を組み立てる。未知のIDでも`DEFAULT_MAZE_STAGE_ID`へ戻し、例外にしない |
| `nextMazeStageId(id)` | カタログ順で次のIDを返す。最後のステージでは`null`を返す |
| `isMazeStageId(value)` | 遷移stateへ入れる値がカタログのIDかを検証する |

ステージを増やすときはカタログへ定義を1件足すだけで、ゲーム本体側にステージIDごとの分岐を増やしません。`MAZE_STAGES`を選択UI・遷移state・次ステージ導線・テストが共通して参照するため、データと表示順も1か所で揃います。

### ステージ設計の制約

- 回転棒の掃引半径は`Math.hypot(SPINNER_LENGTH / 2, SPINNER_THICKNESS / 2)`で約`1.207`です。ボール中心の回避レーンは、棒の中心から`掃引半径 + BALL_RADIUS ≈ 1.837`以上離れる必要があります。したがって1〜2マス幅の通路には置けず、少なくとも3マス幅の部屋へ置き、棒を片側へ寄せて反対側に逃げ道を残します。
- `buildWallRects`は壁を**横方向にだけ**マージします。たとえば5マスの縦内壁は5個のコライダー、5マスの横内壁は1個です。内壁は横長にするとコライダー数を抑えられます。
- 穴の隣を通す道は2マス幅以上にします。穴に両側を挟まれた1マス幅の通路は、幼児向けの復帰間隔でも不公平になるためです。
- `mazeLayout.test.ts`は全ステージを対象に、回転棒の掃引円と壁の非接触、掃引円へ入らずSTARTからGOALへ到達できること、バンパーの余白と間隔、チェックポイントと危険物の距離、ギミックとSTART/GOALの非重複を自動検証します。新しいステージもこのゲートを通す必要があります。

ギミック配置は`resolveGimmicks`で`cellToWorld`を通してワールド座標へ解決します。小数のセル座標も使えるため、棒を通路の中央から少しずらしたり、バンパーを部屋の中で散らしたりできます。座標変換の正本は`mazeGrid.ts`の`CELL_SIZE`と`cellToWorld`に置き、`mazeStage.ts`と`mazeGimmicks.ts`が同じ変換を参照する構造にしました。ステージ全体をギミック側から参照しないで済み、循環importを避けられるためです。

### セルの寸法

コースの寸法は、ボール半径`BALL_RADIUS = 0.63`を基準単位Rとして、Rの倍率で定義しています。通路幅は`CELL_SIZE = 3R = 1.89`で、直角コーナーで軌道が多少ずれても壁へ食い込みにくい片側0.5Rの余白を残します。

| 寸法 | Rに対する倍率 | 実値 | 意図 |
| --- | ---: | ---: | --- |
| 通路幅 `CELL_SIZE` | 3.0R | 1.89 | 直径2Rのボールの左右へ片側0.5Rの余白 |
| 壁の高さ `WALL_HEIGHT` | 2.2R | 1.386 | 直径2Rより高く、最大傾斜でも乗り越えられない |
| 床の厚み `FLOOR_THICKNESS` | 0.95R | 0.599 | 盤面を連続して支え、床を抜けない |
| ゴール判定 `GOAL_RADIUS` | 1.05R | 0.662 | 取りこぼさず、1マスの半分1.5R未満で隣へ広がらない |
| スポーンの浮かせ量 | 0.03R | 0.019 | 初期フレームで床へめり込まない |
| 穴の落下判定 `HOLE_FALL_Y` | -1.8R | -1.134 | 穴へ抜けたことを床面より下で判定する |
| 穴のピット底 `HOLE_PIT_BOTTOM_Y` | -4.2R | -2.646 | ボールの復帰判定より十分下に置く |
| 場外判定の余白 | 2.4R | 1.512 | 外周への接触だけで場外扱いにしない |
| 落下の場外判定 `FALL_OUT_Y` | -9.5R | -5.985 | 通常の跳ね返りで誤判定しない |

ワールドスケール自体は変えていません。見た目の大型化はカメラ距離で行うため（ボール半径をワールド単位で大きくしてもカメラ距離が同じ比率で変わり、見た目は変わらないまま、調整済みの重力・減衰・速度上限だけが相対的にズレてしまう）、Phase 1/2で確定した手触りの定数はそのままです。

`buildWallRects`は横に連続する壁マスを1枚の矩形へまとめてからコライダーと`Mesh`を作ります。`buildFloorRects`は穴を除いたマスを横方向、同じ列範囲が続くときだけ縦方向へまとめます。経路探索（`findMazePath`によるBFS）は、各ステージの最短経路と自動プレイの目標地点に使います。`isMazeSolvable`と`mazeStages.test.ts`は、すべてのカタログ項目に穴を避ける経路があることを固定します。

## 国旗ボール

選んだ国旗は、球面全体へUVラップするのではなく、**球本体 ＋ 長方形の国旗パネル**という「おもちゃの国旗ボール」として貼ります（`src/components/flag-ball/flagPanelBall.ts`）。

Phase 3の最初の実装は、4:3の国旗SVGを球面へ横1.5枚ぶん繰り返してラップする方式でした。しかしUV球は緯度が上がるほど横方向が潰れるため、赤道から外れた意匠が強く歪みます（緯度40°で縦横比が1.31倍、60°で2.0倍、極では潰れて消える）。日本の日の丸が楕円に伸びて国旗として認識できず、追従カメラでボールが大きく映るようになったことで、この歪みがさらに目立つようになりました。

目的は物理的に正確な球面投影ではなく、**転がっている最中でも子どもが国旗を見て判別できること**なので、次の表現に変えました。

- **球面に沿った長方形パッチ**: パネル平面の座標(u, v)を、正面ベクトルから `yaw = u / Rs`、`pitch = v / Rs` の2回転で球面へ写します。中心を通る縦横線の弧長がu, vと厳密に一致するため、国旗の4:3比率が中央で保たれます。パッチ全体でも縦横比の歪みは最大1.116倍に収まり、旧方式の2.0倍以上から大きく改善しています。UVは0〜1の全面で、繰り返しもオフセットも掛けません（＝国旗1枚がまるごと見える）。
- **細い枠線**: 国旗パネルの外側へ`FLAG_PANEL_BORDER_IN_RADII = 0.06`（球半径の6%）ぶん広げた同形のパッチを、わずかに内側の半径へ濃色（`#2b3440`）で敷きます。白地の国旗（日本・カナダ・イギリスの白部分など）が球本体と同化せず、国旗の領域が小さい画面でも明確になります。
- **球本体**: 国旗テクスチャは貼らず、明るいニュートラル色（`#eceff3`）の単色にします。

寸法はすべて球半径Rの倍率で定義しています。パネル幅は`FLAG_PANEL_WIDTH_IN_RADII = 1.24`（球直径の62%、yaw半角35.1°）、高さは幅÷(4/3)です。

### パネル枚数：2枚と4枚の比較

配置は`FLAG_PANEL_LAYOUTS`のデータとして持ち、`two`（前後）と`four`（前後左右）を切り替えられます。仰角58°の見下ろしカメラから「少なくとも1枚が読める（法線とカメラ方向の内積が0.45以上）時間の割合」を、1回転ぶんを3600分割して測った結果は次の通りです（`flagPanelBall.test.ts`が数値を固定しています）。

| 進行方向 | 2枚 | 4枚 |
| --- | ---: | ---: |
| 0°（カメラへ向かって転がる） | 70.3% | 70.3% |
| 45°（斜め） | 40.9% | 81.8% |
| 90°（横切る） | 100% | 100% |

2枚だと斜めに転がるときに国旗が見えない時間が6割近くあり、幼児が「どの国旗を転がしているか」を見失います。4枚は最悪でも70.3%で、見た目がうるさくなる心配も、球直径の62%というパネル幅では起きませんでした。よって`DEFAULT_FLAG_PANEL_LAYOUT = 'four'`を採用しています。隣り合うパネルが球面上で重ならないこと（枠を含めた半幅の2倍が中心間角度90°より小さいこと）もテストで保証しているため、パネル幅を広げすぎる変更は自動で落ちます。

### 国旗SVGは必ずキャンバスへ焼いてからテクスチャにする

国旗SVGの `<img>` をそのままWebGLへ渡すと、**Windows版Chrome(ANGLE/D3D11)などでは `texImage2D` が `INVALID_VALUE` を返し**、テクスチャが不完全なままサンプリングされて国旗パネルが真っ黒になります。同じコードでもiOS/Androidのブラウザでは表示されるため、スマホ実機だけを見ていると気付けません。

そこで `createFlagPanelTexture` は、640×480の2Dキャンバスへ白地を塗ってから `drawImage` でSVGを焼き、その `CanvasTexture` を返します。ラスタライズを挟めばどのブラウザでも同じようにアップロードできます。副次的な利点として、flag-iconsのSVGは `width`/`height` を持たず既定では200×150程度にしかラスタライズされないため、viewBoxと同じ640×480で焼くことで解像度も上がります。下地を白で塗るのは、画像が届くまでの透明な状態がそのまま黒いパネルに見えるのを防ぐためです。

### 国旗データの扱い

国名・SVGパス・円形表示の調整は既存の`src/components/flag-ball/flagBalls.ts`（flag-quizの105か国マスター＋補足2か国）から来る`FlagBallData`をそのまま使い、このゲーム専用の国リストや色テーブルは持ちません。なお、円形にクロップするときの横位置調整`ballPositionX`はパネル方式では不要になったため、3Dボール側では参照していません（CSS版の`FlagBall.tsx`は引き続き使います）。

## 子ども向けの操作感

「難しくするより触っていて気持ちいいこと」を優先し、実測できる数値で手触りを決めています（`mazePhysics.ts`）。

| 項目 | 値 | 意図 |
| --- | ---: | --- |
| 最大傾き角 `MAX_TILT_RAD` | 18° | 最大入力でも盤面はこれ以上傾かない |
| 重力の大きさ `GRAVITY_MAGNITUDE` | 12 | 幼児が目で追いかけられる速さで転がる、実スケールより弱い重力 |
| 最大傾きでの転がり加速度（概算） | 約2.65 | 一様な球の転がり加速度 `(5/7)·g·sinθ` から算出。1〜3の範囲に収まるようテストで固定 |
| デッドゾーン `TILT_DEADZONE` | 0.18 | 指を完全に中央へ戻せなくても「離したら止まる」を成立させる |
| 速度上限 `MAX_BALL_SPEED` | 5.4 | すり抜けと「速すぎて操作できない」を同時に防ぐ |
| 線形減衰 `BALL_LINEAR_DAMPING` | 0.42 | 転がり続けても加速し切らない |
| 角減衰 `BALL_ANGULAR_DAMPING` | 0.55 | 回転が暴れない |
| 入力の平滑化係数 `TILT_SMOOTHING_LAMBDA` | 9（1/秒） | 入力が飛んでも重力が階段状に切り替わらない |
| 見た目の傾き比率 `VISUAL_TILT_RATIO` | 0.62 | 物理の傾きより浅く見せて酔いにくくする |

反発は壁・床ともにほぼ殺しています（`BALL_RESTITUTION = 0.08`、`WALL_RESTITUTION = 0.02`）。壁で跳ね返って進行方向を見失わないようにするためです。摩擦は逆に高め（`BALL_FRICTION = 0.7`、`FLOOR_FRICTION = 0.85`）にして、滑るのではなく転がる感触にしています。

## 落下・復帰とスタック対策

- **外周壁**: ステージは必ず外周を`#`で囲み、盤面の外へ転がり出る通常経路を作りません。
- **チェックポイント**: 各`MazeStageDefinition`の`checkpointCells`をワールド座標へ変換した`stage.checkpoints`を、スタートから前進する順番で持ちます。`updateCheckpointTracker`は次のチェックポイントだけを確認し、水平距離が`CHECKPOINT_RADIUS = CELL_SIZE * 0.75`以内へ入ったときだけ通過記録を進めます。いったん進んだ`index`は後戻りさせません。
- **落下時の即時復帰**: 穴は`hasFallenBelowFloor`が`HOLE_FALL_Y = -BALL_RADIUS * 1.8`より下へ抜けた時点で検出します。外周からの場外は`hasFallenOut`が`FALL_OUT_Y = -BALL_RADIUS * 9.5`より下、または盤面境界から`BALL_RADIUS * OUT_OF_BOUNDS_MARGIN_IN_RADII`（`OUT_OF_BOUNDS_MARGIN_IN_RADII = 2.4`）を超えたときに検出します。検出すると`useMazeEngine`の`rescueToCheckpoint`が最後に通過したチェックポイントへ`resetBall`し、速度と角速度を消して、カメラもその位置へスナップします。ゲームオーバー画面や長い待ち時間は挟まず、`onRescue`で短い通知だけを出して遊びを続けます。
- **復帰直後の猶予と落ち着き**: `RESPAWN_GRACE_MS = 350`msは、同じ穴・場外やスタック判定を復帰直後に連続して拾わないための猶予です。`RESPAWN_SETTLE_MS = 500`msは、重力と入力を保持したまま毎フレームの速度・角速度を0にし、幼児が次に進む方向を把握するための落ち着き時間です。どちらもゲームオーバーを表示するための待ち時間ではなく、復帰位置を安全に受け入れるための短い時間です。
- **停滞からのエスカレーション**: `updateStallTracker`は、入力の大きさが`STALL_TILT_THRESHOLD = 0.45`以上なのに速さが`STALL_SPEED = 0.12`未満の状態が`STALL_DURATION_MS = 1400`ms続いたら、`nudgeBall`で傾けている方向へ強さ`0.12`の弱いナッジを出します。ナッジ後は停滞時間をリセットし、3回（`STALL_RESCUE_NUDGE_COUNT = 3`）検出しても動かなければ復帰へ切り替えます。触っていないときは停滞由来の救済を発火しないので、子どもが意図的に止めている時間を邪魔しません。
- **回転棒の掃引円からの脱出**: 棒の`sweepRadius + BALL_RADIUS`以内に同じ回転棒がある状態を`SPINNER_TRAP_MS = 3000`ms続けると、`pushBallOutOfSpinner`で中心から外向きへ強さ`1.6`の押し出しを行います。それでも同じ棒の圏内に残って2回（`SPINNER_TRAP_ESCAPE_LIMIT = 2`）失敗したら、スタックとしてチェックポイントへ復帰します。速度が出ていても棒に回され続けるケースを、停滞判定とは別に拾うための仕組みです。
- **配置の安全性をテストで保証**: `mazeLayout.test.ts`で全ステージについて、回転棒の掃引円が壁へ食い込まないこと、掃引円へ入らずSTARTからGOALまで到達できること、バンパーと壁・ほかのバンパーとの距離、チェックポイントが壁・穴・ギミックから離れていることを検証します。ぼうけんステージについては、縦通路に穴のない連続レーンが1本（列7）あり、その幅がボール直径以上であることも個別に検証します。**「回転棒は必ず避けられる隙間を残す」ことは、幼児がギミックで詰まらないための必須条件です。**
- **いつでも押せる「スタートに もどる」**: プレイ中は常時表示され、物理世界を作り直さずにボールだけをスタートへ戻します（`resetBallToStart`）。これはチェックポイント復帰とは別の、ユーザーが任意にやり直す操作です。
- **ゴール後の「もういちど」**: `runId`を更新して`useMazeEngine`のエフェクトを丸ごと作り直し、物理世界・カメラ・傾き状態を最初の状態に揃えます。

## アクセシビリティと画面サイズ

- **キーボード操作**: 矢印キー／WASD（`TILT_KEY_CODES`）で操作でき、`FlagRollMazePlay.tsx`側でキー押下状態を集計して`TiltInput`へ変換します。矢印キーでのページスクロールは`preventDefault`で止め、タブを離れた（`blur`）ときは押しっぱなし状態をクリアします。
- **通知**: ゴール文言（「ゴール！ すごい！」）と場外復帰メッセージ（「スタートに もどったよ」）はいずれも`role="status"`と`aria-live="polite"`を付けています。
- **タップ領域**: 操作ボタンは`min-height: var(--tap-target-min)`。ズームの`＋ / −`は補助操作なので52px（低い横画面では44px）にし、主操作より小さく、規約の補助操作44px以上は満たす大きさにしています。装飾の記号は`aria-hidden`にし、`aria-label`で読み上げます。バーチャルスティックは`min(34vw, 148px)`（最小120px）で、規約の主操作64px以上を満たします。
- **`prefers-reduced-motion`**: バーチャルスティックのノブが指を離したあと中央へ戻る`transition`（`VirtualStick.module.css`）は`prefers-reduced-motion: reduce`で無効化されます。ボール自体の転がりはCSSアニメーションではなく物理演算そのもの（ゲームの本質的な動き）なので対象にしていません。全画面共通の`global.css`側の`prefers-reduced-motion`ルールもCSSの`transition`/`animation`を対象にしており、同じ扱いです。
- **画面の高さ**: `.page`は`min-height`ではなく`height: 100dvh`で、3Dシーンのcanvasは`position: absolute`で敷きます。あわせて`renderer.setSize(width, height, false)`（第3引数false）でcanvasへ幅・高さのインラインstyleを書かせず、**表示サイズはCSSだけが決め、レンダラは解像度を合わせるだけ**にしています。`min-height` + インラインstyleの組み合わせだと「canvasの高さ→シーン行の高さ→ページの高さ→測り直したcanvasの高さ」という循環ができ、縦画面で決まった高さが横画面へ持ち越されて、回転後に盤面や操作系が画面からはみ出していました。
- **向きの切り替えへの追従**: 3Dシーンとカメラは`ResizeObserver`に加えて、`window`の`resize`／`orientationchange`、`screen.orientation`の`change`、`visualViewport`の`resize`からも測り直します。回転直後はまだ回転前のサイズを返す端末（特にiOS Safari）があるため、`sceneResize.ts`の`createResizeScheduler`が即時に1回、さらに0/120/320ms後にも測り直します。`computeMazeCameraDistance`がその時点のaspectからカメラ距離を計算し直すので、縦でも横でもボールが同じ大きさで見えます。注視点の追従は毎フレーム続くため、回転中もボールを見失いません。
- **狭い縦画面・低い横画面**: `orientation: landscape`かつ`max-height: 600px`では、スティック／3Dシーン／ボタンの横3カラムへ組み替え、説明文とキーボードヒントを隠して見出しを縮小します。`max-width: 360px`ではボタンの左右の余白を詰めます。
- **バーチャルスティックの`aria-hidden`**: `VirtualStick`のルート要素は`aria-hidden="true"`です。矢印キー／WASDによるキーボード操作を別に用意しているポインタ専用の見た目のため、スクリーンリーダーには操作可能な要素として読み上げさせません。

## 素材

盤面・壁・ゴールはThree.jsのプリミティブ形状（`BoxGeometry` / `CylinderGeometry` / `SphereGeometry`）と単色の`MeshLambertMaterial`で表現しています。国旗パネルのテクスチャは、既存の`public/flags/*.svg`（こっきクイズ・こっきピンボールなどと共有しているflag-icons由来の素材）をそのまま読み込みます。このゲーム専用の新規バイナリアセットは追加していないため、`docs/CREDITS.md`への追記は不要です。

## PWA

国旗SVGは既存ゲームがすでにprecache対象にしているため、`vite.config.ts`のWorkbox `globPatterns`の変更は不要です。国旗パスは`import.meta.env.BASE_URL`を前置きして解決するので、GitHub Pagesのようなサブパス配信でも壊れません。Rapierのwasmは`rapier.mjs`へbase64で埋め込まれた形でJSバンドルの一部として配信され、既存の`domino-flag`（こっきドミノ）と同じインスタンス初期化コード（モジュール内で一度だけ`RAPIER.init()`する仕組み）を、それぞれのゲームが自分のモジュール内に持つ形で共有しています。

## Phase 6以降への引き継ぎ

- **新しいギミック種別**: シーソー・動く床などは未実装です。Issue #125の例にあった「でこぼこステージ」は、新しい物理ギミックを急いで足さず、既存の穴を中心にした`anaana`として実装しました。新しい種別を追加するときも、まず`GimmickPlacement`と`resolveGimmicks`、物理ワールド、配置安全性テストを同じ順で拡張します。
- **クリア状況の保存**: 現在は選んだステージをその場で遊ぶだけで、到達済みステージや星などの進捗を保存しません。保存を足すときは、カタログの安定した`id`をキーにして、選択画面へ過剰な説明を増やさない見せ方を検討します。
- **結果画面とBGM**: ゴール後はプレイ画面内の導線だけで、専用の結果画面・BGMはありません。効果音の追加、ゴール時のアニメーション、背景の作り込みも次の候補です。
- **カメラ**: 距離も注視点もステージの形に依存しないので、坂・橋・トンネル・上下差のような高さのある要素を足すときは、注視点の高さ（現在は`BALL_RADIUS`固定）をボールの高さへ追従させるかどうかだけを検討すればよいです。
- **国旗パネル**: 枚数と配置は`FLAG_PANEL_LAYOUTS`のデータなので、球をさらに大きくする／小さくする変更をしたときは、可視性テストの数値を見ながら2枚へ戻すこともできます。
