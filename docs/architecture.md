# アーキテクチャ

> この文書は長期的な設計・運用方針を扱う。個別機能の最新仕様は GitHub Issue、現在の詳細挙動・パラメータは実装コードとテストを正とする。

## 全体像

kids-playground は React + TypeScript + Vite で構築した、幼児・子ども向けミニゲーム集の静的Webアプリです。バックエンド・DB・外部APIを基本的に持たず、ビルド成果物を静的ホスティングへ配置するだけで完結する構成を前提にしています。この前提が以降のすべての設計判断（ルーティング、状態管理、素材の同梱方針）の土台になっています。

## ゲームカタログを単一情報源とする構造

各ミニゲームは `src/games/gameCatalog.ts` の一覧に1件登録することで、ホーム画面のカード表示・ルーティング・ビルド時の静的ページ生成・SEO用メタ情報が同時に揃うようになっています。ゲームの一覧や個別仕様をこのファイル以外の場所（README・docs）へ重複して書き出さないことが、増減のたびに複数箇所を保守しなくて済む前提になっています。カタログのエントリは表示用の説明文とSEO用の情報をあわせ持つ型になっており、片方だけを書き漏らすと型エラーになる構造です。

## ルーティング方針

React Router のブラウザ履歴ベースのルーティングを採用し、各ゲームは `/games/<game-id>` 以下の固有パスURLを持ちます。静的ホスティングはサーバー側ルーティングを持たないため、ビルド時にゲームごとの静的HTMLと、より深い階層のURL向けのSPAフォールバックを生成することで、直接アクセスやリロードが破綻しないようにしています。旧ルーティング方式で使っていたURLからの互換リダイレクトも用意しています。

## SEO の単一情報源

ページごとのメタ情報（タイトル・説明・canonical・構造化データなど）は、ゲームカタログが持つ定義から導出します。画面表示用の文言とSEO用の文言を別々に管理せず、同じ情報源から組み立てる方針です。サイトマップやrobots設定も同じカタログとURL組み立てロジックから生成し、ゲーム追加時の更新漏れが起きない構造にしています。

## PWA とオフラインの方針

アプリ本体・主要な静的素材をキャッシュし、オフラインでも遊べることを基本方針とします。3Dゲームが利用する物理エンジンのWASMなど、単体で大きい素材があることはキャッシュ構成上の制約になるため、新しい大きな素材を追加する際はオフライン成立とキャッシュ容量への影響を確認します。更新の反映はプレイ中の進行を壊さないよう、ユーザー操作を挟んでから行う方針です。個々のキャッシュ対象・上限値はビルド設定を正とし、ここには書きません。

## 描画・物理ライブラリの使い分け

表現に応じてライブラリを使い分け、全ゲームを1つの技術に統一しないことを設計判断としています。

- DOM/CSSで表現できるものは素の DOM を使う。
- 2D物理演算が必要なものは軽量な2D物理エンジンを使う。
- 3D表現・3D物理演算が必要なものは3Dレンダリングライブラリと、必要な場合のみ3D物理エンジンを組み合わせる。

どのゲームがどのライブラリを使うかの一覧はここでは持たず、各ゲームのコードを正とします。

## 状態と保存の方針

バックエンド・DBを持たないため、端末をまたがない保存が必要な情報はブラウザのローカルストレージのみで扱います。保存が必要かどうかは「サーバーが無くても成立するか」「無くても遊びとして破綻しないか」を基準に判断します。

## 音声・読み上げの方針

音声読み上げ機能を使う場合も、音が出ない・利用できない環境でゲームが成立することを必須要件とします。音声はあくまで補助であり、視覚的なフィードバック（色・記号・文言）だけで遊びが完結する設計を維持します。

## 設計上の重要方針

- **シンプルにする**: 個人開発規模のアプリであるため、必要以上に複雑な抽象化やフレームワークを持ち込まない。
- **過度に共通化しない**: 複数のゲームで同じ意味・同じ変更理由を持つ処理が現れてから共通化する。将来の用途だけを想定した抽象化は作らない。
- **ゲーム固有処理を分離する**: 各ゲームの画面・ロジック・データは `src/games/<game-id>/` 以下に閉じ、他のゲームや共通基盤へ染み出させない。
- **データとロジックを分離する**: ゲームのマスタデータと、問題生成・進行などのロジックを分離する。
- **UI層と物理・シミュレーション層を分離する**: 物理演算やシミュレーションを使うゲームでは、画面コンポーネントが物理エンジンの内部状態を直接持たず、フックなどの層越しに結果だけを受け取る構造にする。これにより物理エンジンを動かさずに単体テストできる状態を保つ。
- **静的サイトとして完結させる**: ソースコード管理・CI・静的ホスティングの組み合わせだけで公開まで完結する構成を維持する。
