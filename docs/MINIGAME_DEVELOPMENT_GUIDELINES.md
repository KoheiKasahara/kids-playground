# ミニゲーム開発規約

## 1. 目的と適用範囲

この文書は、`kids-playground` に新しい子ども向けミニゲームを追加・変更するときの共通規約です。
画面、ルーティング、問題生成、静的素材、PWA、テスト、文書更新を対象とします。

ゲーム固有の楽しさを保つことを優先し、共通化は複数ゲームで意味と変更理由が一致する最小単位に限定します。
巨大な汎用ゲーム画面や、将来用途だけを想定した抽象化は作りません。

## 2. ディレクトリと責務

```text
src/
├─ app/routes.tsx              # 全ゲームのURL登録
├─ components/                 # 意味が共通するUI部品
├─ games/
│  ├─ quiz-core/               # 小さな4択クイズ共通ロジック・型
│  └─ <game-id>/               # 画面、固有データ、固有ロジック、テスト
└─ utils/                      # 効果音などゲーム横断の機能

public/<asset-group>/          # オフライン利用する静的素材
docs/                          # 設計、運用、素材クレジット
```

- ゲームIDとURLは小文字の kebab-case にする。
- ゲーム固有の表示文、モード、素材データ、レイアウトは `src/games/<game-id>/` に置く。
- 共通化する前に、少なくとも2ゲームで同じ意味・制約・変更理由を持つことを確認する。
- 共通型は固有データを知らない形にする。例: `id` を持つデータ向けの `QuizQuestion<T>`。
- 既存ゲームを共通基盤へ移す場合は互換exportを残し、既存APIとテストを同時に維持する。

## 3. ルーティング

基本URLは次の形にします。

```text
/games/<game-id>                         開始・モード選択
/games/<game-id>/<mode>                  むずかしさ選択
/games/<game-id>/<mode>/:level/play      プレイ
/games/<game-id>/<mode>/:level/result    結果
```

- `:level` は `easy` / `normal` / `hard` のみを受け付ける。
- URLパラメータは型ガードで検証し、不正値は同じモードの設定画面へ `replace` で戻す。
- 結果のように画面遷移stateが必要なURLへ直接アクセスされた場合は、ゲーム開始画面へ安全に戻す。
- GitHub Pagesでの直接リロードを成立させるため、アプリは `HashRouter` を維持する。
- 新規ゲーム追加時はホームのカード、ルート定義、ルートを通すComponent Testを同時に追加する。

## 4. 子ども向けUIとアクセシビリティ

- 画面文言は短くし、難しい漢字を避ける。必要な固有名詞はカタカナを使ってよい。
- 主操作のタップ領域は原則64px以上、補助操作も44px以上にする。
- ボタン同士に十分な間隔を取り、終了操作は問題回答から離して誤操作を避ける。
- マウスだけでなく、標準のボタン要素によるタッチ・キーボード操作を可能にする。
- `:focus-visible` を消さず、背景と識別できるフォーカスリングを表示する。
- 正誤は色だけに頼らず、`◯` / `✕`、文、必要に応じて効果音を併用する。
- 回答結果は `role="status"` と `aria-live="polite"` で通知する。
- 回答後の正誤表示には共通コンポーネント `src/components/QuizResultOverlay.tsx` を使う。
- 下部余白（オーバーレイぶんの `padding-bottom`）は回答したかどうかに依存させず、ビューポートの幅・高さだけで決める（回答前後でレイアウトが動かないようにする）。
- 画像だけの選択肢には、答えを漏らさない位置ベースのアクセシブルネームを付ける。
- 装飾絵文字は `aria-hidden="true"` にする。
- `prefers-reduced-motion` を尊重する。
- 320px程度の狭い縦画面、低い横画面、タブレット、PCで、主要操作が画面外に隠れないことを確認する。

## 5. 出題、むずかしさ、乱数

- 標準は1ゲーム10問、1問4択とする。変更する場合はゲーム設計書に理由を書く。
- 1ゲーム内で正解問題を重複させない。
- 1問の選択肢は重複なしで、正解をちょうど1つ含める。
- `easy < normal < hard` の累積プールを基本とする（かんたん ⊂ ふつう ⊂ むずかしい）。
- むずかしさは選択肢数ではなく、出題対象の広さや内容で調整する。
- Fisher–Yatesなど偏りを増やさない方法でシャッフルし、元データを破壊しない。
- 問題生成関数は乱数関数を注入可能にし、テストではシード付き乱数で再現できるようにする。
- 出題プールは4件以上、10問ゲームでは原則10件以上を品質ゲートとする。

## 6. 素材、権利、クレジット、プライバシー

- 外部ホットリンクを禁止し、利用する素材は `public/` にローカル同梱する。
- Public Domain、CC0、CC BY、CC BY-SAなど、再配布と必要な加工が許される素材だけを採用する。
- 素材ごとに配布元ページ、作者、ライセンス名、ライセンスURLを取得時に確認する。
- 出典や作者を推測・捏造しない。不明な場合は「不明」と明記し、配布元の権利表示で再配布可能かを確認する。
- CC BY / CC BY-SAの加工物は、トリミング・縮小・形式変換などの変更内容をクレジットに記載する。
- CC BY-SAの加工物は同じ、または互換ライセンス条件で再配布する。
- `docs/CREDITS.md` に同梱素材の実データを追加し、素材を差し替えたら同時に更新する。
- 権利不明、透かし付き、人物の顔が主題、判読可能な車両番号・ナンバープレート、企業広告やロゴが主題の素材は避ける。
- 子ども向け用途では人物や個人情報を必要最小限にし、位置情報など不要なEXIFは配布画像から除去する。
- 画像は識別性を保てる範囲で縮小・圧縮し、PWAの容量と表示速度を抑える。

## 7. PWAとGitHub Pages

- 静的素材のパスは先頭スラッシュを付けず、表示時に `import.meta.env.BASE_URL` を足す。
- 新しい拡張子を追加した場合は `vite.config.ts` のWorkbox `globPatterns` を更新する。
- オフラインでゲーム本体と全問題素材が利用できるよう、必要素材をprecache対象にする。
- Workboxの最大ファイルサイズは安易に引き上げず、まず素材を適切に圧縮する。
- 通常ビルドと `GITHUB_PAGES=true` のPages向けビルドを両方確認する。
- 公開やpushは、依頼で明示された場合だけ行う。

## 8. 品質ゲート

変更完了前に次を満たします。

1. データ件数、ID・名前・素材パスの重複、素材実在をUnit Testで確認する。
2. むずかしさ別件数と累積包含関係を確認する。
3. 問題数、4択、正解1件、選択肢・問題の重複なしを確認する。
4. 全モードの表示、回答、進行、結果、再挑戦をComponent Testで確認する。
5. 不正URL、stateなし結果URL、ホームと主要ルートのフォールバックを確認する。
6. 画像の視認性、向き、容量、人物・ナンバー・ロゴを目視確認する。
7. `lint`、`test`、`build`、`build:pages` を実行する。
8. ビルドされたService Workerのprecacheに新素材が含まれ、Workbox警告がないことを確認する。
9. 既存ゲームのテストを含む全テストが通ることを確認する。

## 9. 文書更新とレビュー・チェックリスト

新規ゲームまたは重要仕様の変更時は、README、概要設計、セットアップ、ゲーム基本設計、クレジットを必要な範囲で更新します。

- [ ] 対象年齢、学習・遊びの目的、モードを説明した
- [ ] URLと画面遷移を列挙した
- [ ] 問題数、選択肢数、むずかしさの件数と包含関係を明記した
- [ ] データと素材パスの責務を説明した
- [ ] 全素材の出典・作者・ライセンス・加工を記録した
- [ ] タッチ、キーボード、読み上げ、色以外のフィードバックを確認した
- [ ] 狭い縦画面と低い横画面を確認した
- [ ] PWAとGitHub Pagesのbase pathを確認した
- [ ] Unit / Component Testと4つの検証コマンドを完了した
- [ ] 既存ゲームの互換性と不要な共通化がないことをレビューした
